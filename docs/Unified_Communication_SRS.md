# Unified Communication System — Software Requirements Specification

**Status**: requirements documentation only, 2026-09-23. Grounded directly against real code (`EA`, `ER/Principal/SchoolAdmissions`, `WEB`) and existing project docs — nothing invented, nothing built from this pass. Design/implementation is explicitly deferred to a separate pass, per the instruction this document was commissioned under.

**Scope note on terminology**: this document calls the covered surface the "FiSH+ER-Verse" per the user's own term — the union of every FiSH module (GL/SOP/POP/IM/HR/TAX, all administered through EA) and ER's own systems (currently SchoolAdmissions/"The Principal," under `ER/Principal/`). It is *not* a proposal to merge EA's and SchoolAdmissions' identity models — see §7 Open Questions for why that is named as a question, not resolved here.

---

## 1. Purpose and Scope

This SRS captures requirements for a "reengineered" unified communication system spanning every FiSH tenant and every ER system, elicited directly from the user across six numbered requirements (§4). Three of the six are already built in EA's unified `Message`/`MessageAudience` model (2026-09-19 rebuild, replacing the earlier separate `Announcement`/`ChatMessage`/`SupportMessage` aggregates); three are not built at all. This document's job is to state, per requirement, what exists today (with exact file/class citations), what doesn't, and — critically — how each requirement plays out differently across three organizational shapes a FiSH Tenant can take: a normal (single-Company) company, a conglomerate (multi-Company Tenant), and a school or group of schools (one or more SCHOOL-type Companies under a Tenant).

Out of scope: any technical/API design, database schema, or Kotlin/TypeScript code. This document and its companion `Unified_Communication_Use_Cases.md` are inputs to a future design pass, not the design itself.

## 3. Actors

| Actor | Definition |
|---|---|
| **Tenant Staff (Membership holder)** | A FiSH `User` holding an EA `Membership` in a Tenant — the general staff population able to send/receive most message types, gated by `Role`/`AccessLevel`/`grantedModules` per audience. |
| **Owner-Admin** | Within EA's model, this is not one single fixed identity but two related things that must be told apart (see §7 Q1): (a) `Tenant.businessOwnerId` — exactly one `User` per Tenant, set once at onboarding, never reassigned; (b) any `Membership` holding `Role.OWNER_ADMIN` (there can be more than one — `Tenant.adminMembershipIds` is a set, and the codebase's own KDoc notes "a Tenant can accumulate more than one admin over time"). Both readings currently carry `AccessLevel.ADMIN` by default. |
| **School Staff (ErPrincipal via StaffAssignment)** | A person recognized inside SchoolAdmissions only — resolved via `ErIdentityGateway.resolveForSchool()` against a `StaffAssignment` row (subjectId + schoolId + roles: `TEACHER`, `SCHOOL_ADMIN`, `REGISTRAR`, etc.). Has no necessary relationship to any EA `User`/`Membership` — see §7 Q2. |
| **Platform Operator (Prodeo)** | Not an EA `User` — holds no Membership in any Tenant (per `Message`'s own KDoc: "the platform operator isn't an EA `User`"). Authenticates via a configured operator token (`authorizeOperator`), reachable only through Omniview-side routes. |

## 4. Definitions — the three organizational contexts

- **Normal company**: a Tenant with exactly one Company. Requirement 4 (same-tenant, cross-company communication) is moot here by definition — there is only one Company, so no cross-Company boundary exists to gate.
- **Conglomerate**: a Tenant with more than one Company (the confirmed real-world shape: one production Tenant currently owns 4 Companies — `docs/Tenancy_Administration_Extraction_DDD_Design.md` §3.2's migration note). All 6 requirements are potentially live.
- **School / group of schools**: a Tenant where one or more Companies have `IndustryType.SCHOOL`. Confirmed directly from code (`RegisterCompanyUseCase.execute`, `SchoolAdmissionsGateway.provisionSchool`, `School.organisationId`) that **School provisioning is 1:1 per Company** — `provisionSchool(organisationId = companyId.value.toString(), ...)`, and `School` is documented as "idempotent on `organisationId`," i.e. one School per Company, not per Tenant. So a Tenant with N SCHOOL-type Companies genuinely produces N School rows — a "group of schools" is exactly the conglomerate shape specialized to all-SCHOOL Companies, confirming the mapping the user proposed. Note also (see `School.kt`'s own KDoc): the codebase deliberately treats Company and School as **sibling concepts under a not-yet-modeled "Organisation"**, not a parent/child hierarchy — School isn't a child record of Company, it references the same `CompanyId` value by convention only.

## 5. Functional Requirements

### FR-COMM-01 — 1:1 intra-Tenant direct messaging

**Status: BUILT.** `MessageAudience.Direct(userId)`, sent via `Message.send()`, exposed at `POST/GET /tenants/{tenantId}/messages/direct/{userId}` (`MessageRoutes.kt`).

**Important grounded finding, not assumed**: `Direct` authorization is **Tenant-scoped, not Company-scoped**. `MessageRoutes.kt`'s send handler checks only `membershipRepository.findAllByTenant(tenantId).none { it.userId == targetUserId }` — i.e., "does the target hold *any* Membership in this Tenant?" There is no check against `Membership.companyIds`/`hasAccessToCompany()` anywhere in the Direct path. This has a direct consequence for FR-COMM-04 below.

- **Normal company**: works exactly as built — any two staff members of the one Company (both hold Memberships in the one-Company Tenant) can DM each other.
- **Conglomerate**: also already works as built, but with a consequence worth naming precisely — **a staff member in Company A and a staff member in Company B, both under the same multi-Company Tenant, can already exchange a Direct message today, with no approval gate at all**, because Direct's authorization check never looks at which Company either party belongs to. This appears to be an artifact of Direct being designed around a single-Company mental model, not a deliberate decision to allow unrestricted cross-Company DMs ahead of FR-COMM-04's approval workflow. See §7 Q3.
- **School / group of schools**: works identically to the conglomerate case *for EA Memberships* — e.g., two Business-Owner-side admins of a school Tenant. It does **not** extend to actual school staff (teachers, school admins) recognized only via SchoolAdmissions' `ErPrincipal`/`StaffAssignment` — they hold no EA `User`/`Membership` at all, so there is no `userId` for them to be a `Direct` audience target of. See §7 Q2.

### FR-COMM-02 — 1:many intra-Tenant group chat

**Status: PARTIALLY BUILT.** Three fixed audience shapes exist: `MessageAudience.ForModule(module)` (per-module/team channel — formerly `ChatMessage`), `MessageAudience.ForRole(role)` (broadcast to every active Membership holding a given `Role`), and `MessageAudience.Everyone` (Tenant-wide). All are real, tested, and reachable (`MessageRoutes.kt` `/messages/module/{module}`, `/messages/role/{role}`, `/messages/everyone`; the WEB `SupportChatWidget.tsx` surfaces the module channels and Everyone/"Announcements" today, per its own `CHAT_MODULES` constant and `listModuleMessages`/`listEveryoneMessages`).

**Gap, explicit**: there is no general "create an ad-hoc named group with an arbitrary set of participants" primitive. A Business Owner cannot today spin up, say, a "Q4 Launch Team" channel with five hand-picked people cutting across Roles/Modules/Companies — only the three fixed shapes above.

- **Normal company**: the three fixed shapes cover most single-Company needs (a module team, a role-wide broadcast, everyone). The ad-hoc-group gap is a real but lower-stakes limitation here since there's only one Company's staff to organize.
- **Conglomerate**: **`ForModule` and `ForRole` are also Tenant-wide, not Company-scoped** (`MessageRepository.findAllForModule(tenantId, module)`/`findAllForRole(tenantId, role)` take no Company parameter). In a 4-Company Tenant, a "GL team channel" pools every Company's GL-access staff into one channel — there is no way to stand up a Company-specific GL channel using `ForModule` alone. `MessageAudience.ForCompany` (see FR-COMM-03) is the only Company-scoped audience that exists, and it is a broadcast shape (admin-gated send), not a peer group-chat shape. The ad-hoc-group gap is more acute here: a conglomerate's real organizational need (a team spanning specific people from specific Companies) is not served by any of the three fixed shapes.
- **School / group of schools**: `ManagedModule.EDUCATION_RUNTIME` is a real enum value, auto-granted to every admin Membership when a Company's `IndustryType` is `SCHOOL` (`RegisterCompanyUseCase.grantEducationRuntimeToAdmins`). A `ForModule(EDUCATION_RUNTIME)` channel is therefore technically usable today — but only among EA Users who hold an EA Membership with that module granted (i.e., the Tenant's own admins/delegates), never the school's actual teaching staff, who are SchoolAdmissions-only identities with no EA Membership. The "group chat for a school's staff" the requirement implies (teachers, registrars, a head teacher) cannot be built on `ForModule` at all without resolving the identity-bridging question in §7 Q2.

### FR-COMM-03 — Intra-Tenant announcements/broadcasts

**Status: BUILT.** `MessageAudience.Everyone`, admin-gated to send via `authorizeTenantForAdmin` (`MessageRoutes.kt` `POST /tenants/{tenantId}/messages/everyone`), read-gated via `authorizeTenantForRead`. Surfaced in WEB as the "Announcements" channel in `SupportChatWidget.tsx`.

- **Normal company**: `Everyone` broadcasts to the one Company's whole staff — matches intent directly.
- **Conglomerate**: `Everyone` broadcasts across **every** Company under the Tenant at once. `MessageAudience.ForCompany(companyId)` already exists as a second, genuinely Company-scoped broadcast audience (admin-gated send at `/messages/company/{companyId}`, with an explicit `membership.hasAccessToCompany(companyId)` check on both send and read) — this is real, built, and directly answers the conglomerate need for a "broadcast to just Company B's staff" the bare `Everyone` audience can't serve alone. Worth naming explicitly since the user's six numbered requirements don't call out `ForCompany` by name, but it is the mechanism that makes requirement 3 actually work correctly in the conglomerate context.
- **School / group of schools**: `Everyone`/`ForCompany` broadcast to EA Memberships exactly as in the conglomerate case. Neither reaches SchoolAdmissions-only staff (teachers) for the same identity-gap reason as FR-COMM-02.

### FR-COMM-04 — Same-Tenant, cross-Company staff communication gated by Owner-Admin approval

**Status: NOT BUILT.** No request/approval lifecycle of any kind exists in `EA`'s communication domain today — `Message`/`MessageAudience` has no notion of a pending, unapproved conversation. This is a genuine gap, not a partial build.

The user's stated intent: staff member in Company A wants to reach a specific staff member (or, presumably, more broadly, staff) in Company B of the same Tenant; a request is raised; the Owner-Admin must explicitly approve **that specific conversation** (not a standing Company-pair rule, not a platform-wide toggle) before messaging opens between the two parties. This implies a real state machine: **Requested → Pending Approval → Approved (messaging opens) / Denied (messaging never opens)**.

- **Normal company**: moot by definition — there is only one Company, so there is no cross-Company boundary for this requirement to gate. No behavior is needed here.
- **Conglomerate**: this is requirement 4's primary and only live context. As noted under FR-COMM-01, this requirement is complicated in practice by the fact that **`MessageAudience.Direct` already lets any two Tenant Memberships message each other regardless of Company, with no gate whatsoever** — so building the approval workflow does not, by itself, close a channel that's already open. Whether the intended design tightens `Direct` to require same-Company (or an approved cross-Company grant) before it's usable, or leaves `Direct` as-is and adds an entirely separate gated audience/mechanism on top (in which case the pre-existing unrestricted `Direct` channel would still bypass the new approval requirement entirely), is not decided here — see §7 Q3. This document deliberately does not pick an answer.
- **School / group of schools**: for a Tenant with multiple SCHOOL-type Companies (the "group of schools" case), the natural real-world analogue is a staff member at School X wanting to reach a staff member at School Y within the same group. But since school staff are recognized entirely through SchoolAdmissions' own `ErPrincipal`/`StaffAssignment` model (scoped to one `SchoolId`, keyed by `subjectId`), not EA's `Membership`, **there is no existing party for a cross-Company approval workflow to name on the school-staff side at all** — the same identity gap as FR-COMM-01/02, compounding requirement 4's own approval-workflow gap. Two layered problems, not one.

### FR-COMM-05 — Cross-Tenant communication, Owner-Admin ↔ Owner-Admin only

**Status: NOT BUILT, and blocked on a real prerequisite.** Confirmed directly against `EA/src/main/kotlin/com/theprodeogroup/ea/domain/tenancy/repositories.kt`: every repository method is scoped to a single Tenant or a single id (`TenantRepository.findById`, `UserRepository.findById`/`findByEmail`, `MembershipRepository.findById`/`findAllByTenant`). **There is no cross-tenant query method anywhere** — no "list other Tenants," no "find a Tenant by some public identifier," nothing. This exact gap was already named and deliberately parked in `docs/Inter_Tenant_Trade_Automation_Vision.md`: *"POP's `Supplier` and SOP's `Customer` are each scoped to a single tenant's own bounded context today, with no notion that a Supplier record might correspond to an actual other Tenant/Company elsewhere in FiSH. There is no cross-tenant identity concept anywhere in the current design"* — and that document's own gating condition (*"revisit this once FiSH has at least two real, paying tenants... who have actually expressed interest in trading with each other"*) applies with equal force to cross-tenant **communication**, not just cross-tenant trade documents. This SRS does not re-derive that finding; it cites it as the governing precedent.

- **All three contexts** are equally blocked by the same prerequisite: there is no discovery mechanism for one Tenant's Owner-Admin to even locate another Tenant to contact, let alone a consent/trust layer gating it. The organizational-shape distinctions (normal/conglomerate/school) don't materially change this requirement's analysis — the blocker sits below all three, at the "does cross-tenant identity exist at all" layer.
- One requirement-specific nuance worth naming for a future design pass (not resolved here): the user specified Owner-Admin-only, not any staff member — narrower than the general cross-tenant trade-automation vision, which is between arbitrary trading-partner records (`Supplier`/`Customer`). A future discovery/consent mechanism for this requirement could plausibly be narrower in scope than what `Inter_Tenant_Trade_Automation_Vision.md` describes (two named individuals, not a full trading-partner relationship) — but that is a genuinely open design question, not something this document decides.

### FR-COMM-06 — Request support from the Platform Operator

**Status: BUILT.** `MessageAudience.OperatorThread`, with `Message.sendToOperatorThread()`/`Message.sendFromOperator()` as the two directions (the latter is the one case with `senderId = null`, matching `Message`'s own KDoc: "the platform operator isn't an EA `User`... so there's no `UserId` to record for their half of that one conversation"). Tenant-side surface: `POST/GET /tenants/{tenantId}/support-thread/messages` (`MessageRoutes.kt`). Operator-side surface: `POST /operator/tenants/{tenantId}/support-thread/messages` and `GET /operator/support-threads` (a flat, cross-Tenant, oldest-first inbox) in `OperatorMessagesRoutes.kt`, gated by `authorizeOperator`, alongside `OperatorTenantOverviewRoutes.kt`/`OperatorPlatformHealthRoutes.kt` under the same operator-token gate — together these three route files are "Omniview," per `OperatorMessagesRoutes.kt`'s own KDoc ("Omniview's own half of the operator-support conversation... alongside `operatorTenantOverviewRoutes`/`operatorPlatformHealthRoutes`").

Current UX, confirmed directly from `WEB/src/components/SupportChatWidget.tsx`/`WEB/src/api/messages.ts`: a floating chat widget (`💬` toggle button, bottom of screen, rendered globally in `App.tsx` "alongside `<Footer/>`/`<ThemeToggle/>`") with a "Support" channel as its default tab, polling every 15 seconds while open (not real-time), styled as mine-vs-theirs bubbles keyed on `fromOperator`. This is baseline/reference behavior, not something this document proposes changing.

- **All three contexts** behave identically — the operator-support channel is Tenant-scoped by construction (`tenantId` on the route, `Tenant`-wide, not Company- or School-specific), and nothing about a Tenant's internal shape (single Company, multiple Companies, school or not) changes how a Tenant reaches Prodeo support. No context-specific variation to record for this requirement.

## 6. Non-Functional Considerations

Only the considerations genuinely raised by grounding this document against real code — not generic NFR boilerplate:

- **Tenant-isolation boundary, already established and worth preserving deliberately for FR-COMM-04/05**: every existing `authorizeTenantFor*` gate (`Auth.kt`) operates within one `tenantId` path parameter. FR-COMM-04's approval workflow and FR-COMM-05's cross-tenant contact both require *deliberately, narrowly* crossing that boundary — the existing gates were not built with any notion of "authorized to reach into a different Tenant," and a future design must not treat crossing this boundary as a minor extension of an existing gate; it is a new kind of trust decision, matching `Inter_Tenant_Trade_Automation_Vision.md`'s own conclusion that intra-tenant service-account trust ("one Tenant's own plumbing") does not extend to inter-tenant calls.
- **Audit trail for the approval workflow (FR-COMM-04)**: because an Owner-Admin's approval is explicitly per-conversation, not a standing rule, any future design needs the approval decision (who requested, who approved/denied, when) to be reconstructable — the same "traceability" expectation this project's other approval-gated workflows already carry (e.g. SOP's aval-confirmation control, NFR-SO01/NFR-SO02 in `SOP/docs/Sales_Order_Processing_Requirements_Use_Cases.md`).
- **Abuse-resistance for cross-tenant discovery (FR-COMM-05)**: `Inter_Tenant_Trade_Automation_Vision.md` already flags this precisely for the trade-automation case ("Audit trail and rate limiting — ... the mechanism needs abuse-resistance from day one, not retrofitted after a problem") — the same concern applies to any future Tenant-discovery mechanism built for Owner-Admin-to-Owner-Admin contact, since a discovery surface is inherently open to enumeration/spam risk regardless of what it's used for.
- Everything else typically listed under NFRs (performance, availability, generic security) is not meaningfully differentiated by this feature relative to the rest of the platform and is deliberately not padded in here.

## 7. Open Questions

Recorded rather than answered, per this project's own established convention of parking genuine unknowns instead of guessing.

1. ~~Which "Owner-Admin" does FR-COMM-04/FR-COMM-05 actually mean?~~ **RESOLVED, 2026-09-23, direct instruction: "The OWNER_ADMIN = Tenant."** Approval authority for FR-COMM-04 (and, by extension, FR-COMM-05) is `Tenant.businessOwnerId` specifically — the one, fixed founding admin `User` per Tenant. This matches this project's existing convention that the Tenant *is* the Business Owner's own identity/perspective (see `feedback_entrepreneur_not_tenant` memory).

   **Refined further, same day, direct instruction: "Only one owner_admin per organisation for now. Multiple admins can exist but only one owner_admin."** This resolves what was previously an open ambiguity (a Tenant *could* have more than one `Role.OWNER_ADMIN` Membership, per `Tenant.adminMembershipIds` being a set) — going forward, `Role.OWNER_ADMIN` itself is constrained to exactly one Membership per Tenant, the `businessOwnerId` one. Other staff may hold `AccessLevel.ADMIN` (broad access) but not the `OWNER_ADMIN` role tag. Real implementation consequence: `TenantRoutes.kt`'s current "an existing Owner/Admin can invite another Owner/Admin" path needs to actually enforce this — an existing OWNER_ADMIN inviting a *second* OWNER_ADMIN-role Membership should now be rejected, not permitted.

   **Future capability, explicitly not built now**: "an admin can be promoted to Owner_Admin, but the incumbent Owner_Admin will be demoted to Admin" — a succession/transfer mechanism, one Owner_Admin at a time. Not scoped or designed here; flagged only so `businessOwnerId`/`Role.OWNER_ADMIN` aren't treated as permanently immutable-by-design when this or a future pass touches that code. Concretely: `Tenant.businessOwnerId`'s own KDoc currently states it is "set once at onboarding, never reassigned" — that specific claim will need revisiting whenever the transfer mechanism is actually built, though not necessarily now.

   Implementation consequence for UC-COMM-07: the approve/deny action must resolve the acting Membership's `userId` against `Tenant.businessOwnerId`, not merely check `Role`/`AccessLevel`.
2. **The EA/SchoolAdmissions identity-bridging question — the central open item this document surfaces.** EA's identity model (`User`/`Membership`, keyed to a `Tenant`) and SchoolAdmissions' identity model (`ErPrincipal`/`StaffAssignment`, keyed to a `SchoolId` + `subjectId`) are completely separate today, with no shared identity except the one-way, fire-and-forget `POST /schools` provisioning call (which passes `organisationId`/`tenantId`/`name` but establishes no ongoing link back to any person). Concretely: **who is the actual party in a 1-to-1 DM between two teachers at the same school?** Is that even an EA `Message` at all (implying every teacher would need an EA `User`/`Membership`, which nothing today creates), or does SchoolAdmissions need its own, entirely separate messaging equivalent, or does some future bridged/federated identity need to exist so one person can be recognized as both an EA Membership holder and a SchoolAdmissions `ErPrincipal`? This document does not pick an answer — it is the single largest unresolved dependency surfaced by researching these six requirements against the school/group-of-schools context.
3. ~~Does closing FR-COMM-04 require tightening `MessageAudience.Direct`?~~ **RESOLVED, 2026-09-23: yes — `Direct` gets a real Company-boundary check, not a parallel channel left alongside an unrestricted one.** Same-Company `Direct` is unaffected; cross-Company `Direct` requires an Approved conversation to exist for that specific pair.

   **This resolution surfaced a much larger, preceding dependency, however.** Determining "same-Company or cross-Company" requires knowing each Membership's home Company — and grounding that question against `Membership.companyIds` (an access-restriction list, nullable = unrestricted) surfaced that it cannot represent this fact as-is. Working through it with the user resolved several deeper points, in order:
   - `companyIds = null` (unrestricted) is **illegitimate for ordinary staff** — that state is reserved for the Owner-Admin only, who is exempt from all of this by sitting above every Company under their Tenant by definition ("Every staff must have RBAC which means he belongs to a company. You cannot be in the FiSH+ERVerse without having a role in an organisation").
   - Staff **can** legitimately be assigned to more than one Company under the same Tenant ("The same staff can be invited to hold roles across a tenancy").
   - **Critically, those roles can genuinely differ per Company** — the same person could be "Manager" at one Company and "Accountant" at another, not one `Role` replicated across a `companyIds` set. Today's `Membership` has exactly one `Role`/`AccessLevel` for its *entire* `companyIds` set — it cannot represent this at all.
   - The invite flow (`InviteStaffMemberUseCase`) itself was reframed, direct correction: it is not "join the Tenant, optionally scoped to a Company" — it is "there's a Role to do at a specific Company, and that's what the invitation actually is." Company assignment needs the same standing as `role` already has in the invite request, not optional-field treatment.

   **This is no longer a small tightening — it's a restructuring of `Membership` itself** (per-Company Role, not Tenant-wide Role), which is now scoped as **its own preceding piece of work**, ordered before FR-COMM-04's build (T3-T5) can start at all — see `FiSH/docs/Per_Company_RBAC_Design.md` (commissioned 2026-09-23) for the full grounded blast-radius analysis and dependency-ordered task list. FR-COMM-04's own task list (T3: conversation-request state machine, T4: Owner-Admin approve/deny, T5: tighten `Direct`) is unchanged in shape, but now depends on that document's own tasks landing first.
4. **Scope of a future ad-hoc group-chat primitive (FR-COMM-02's gap).** Should an ad-hoc named group be restricted to one Company's Membership set, allowed to span an entire Tenant (all Companies), or — in light of Q3 above — subject to the same cross-Company approval gate FR-COMM-04 introduces? Not decided; this document only names the gap, not its resolution.
5. **Does FR-COMM-05's Owner-Admin-only cross-tenant contact need its own, narrower discovery/consent mechanism, or should it wait for and reuse whatever trading-partner discovery mechanism `Inter_Tenant_Trade_Automation_Vision.md` eventually builds for PO→SO automation?** Both are blocked on the same underlying "no cross-tenant identity exists" gap, but they may not need the same solution shape — a two-person contact-request flow is a much smaller trust surface than a full trading-partner relationship.

   **Candidate mechanism surfaced 2026-09-23, not yet decided**: a directory/"follow" model — Owner-Admin X can initiate contact with another Tenant's Owner-Admin Y, but **Y must explicitly approve before the conversation opens** (consent sits with the receiving Owner-Admin, not a third party — a different shape from FR-COMM-04, where a Company's own Owner-Admin approves *other people's* conversations). Once approved/followed, the two communicate directly with no further per-message approval. If adopted, this relationship would itself *be* the discovery/consent layer Question 5 asks about, and FR-COMM-05 would no longer need to wait for `Inter_Tenant_Trade_Automation_Vision.md`'s own gating condition.

   Also stated directly: **"the ethics of the FiSH+ER-Verse expect that it will be professional"** — a values/conduct expectation for this specific channel (Owner-Admin-to-Owner-Admin, cross-Tenant), not yet a technical requirement, but worth carrying into whatever design eventually addresses this (e.g., a stated purpose/reason field on the contact request, or a future conduct-reporting path) rather than dropping it.

   **Explicitly parked, direct instruction: resolve this only after FR-COMM-04 (the same-Tenant cross-Company approval workflow, T1-T5) is done.** Recorded here so the idea isn't lost, not to be designed further until then.
6. **What happens to `ManagedModule.EDUCATION_RUNTIME` team-chat access if Company `industryType` could ever change?** Out of scope for this document (industry type is immutable once set, per `IndustryType`'s own KDoc), but noted since it would interact with any future school-staff messaging design.
