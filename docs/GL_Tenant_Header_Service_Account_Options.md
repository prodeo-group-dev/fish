# GL: the Tenant header and service accounts. Two held options, input to the RBAC SPUTO

**Status: 2026-10-08. Docs only; nothing built.** Written by the GL session at CM's request, as input to the system-wide RBAC SPUTO. Both options below are **on hold** under CM's freeze on authorization-model changes. They came out of IM's finding that it posted every receipt, issue and adjustment to one GL Company fixed at deploy time, and Femi's follow-up question: given only a Company id, how does a caller learn that Company's Tenant id?

## The rule GL applies today (read from GL master `b4723da`)

Every Company-scoped GL route does four things in order: (1) `resolveTenantForCompany` derives the owning Tenant from the Company (404 if the Company does not exist); (2) `verifyClaimedTenant` requires the caller to send an `X-Tenant-Id` header and compares it with that owning Tenant (400 if missing, 403 "X-Tenant-Id does not own the requested resource" if different); (3) for a **person**, `authorizeTenantFor{Read,Write,...}` asks EA for their Membership and checks access level and module grant at that Company; (4) for a **service account** (the SOP, POP, IM and HR credentials, and the Education Runtime's own), step 3 is skipped by design (`docs/Service_Account_Identity_And_EA_Membership_Design_Note.md`). So for a service credential the header is the **only per-request tenancy assertion**: the caller states which business it believes it is acting for, and GL confirms the Company really belongs to that business. Every service fixes that header's value at deploy time, so each service can only act inside its configured Tenant. A Company under a different Tenant is refused, which is correct, but it also means a service cannot work across Tenants. No GL read route returns a Company's Tenant id to a service credential (`GET /me` does, but only for a signed-in person).

## Option A: service accounts may omit the header (GL derives the Tenant from the Company)

If the header is absent on a service-account call, GL skips the comparison (it already knows the owning Tenant from step 1); if the header is present it is still compared exactly as today, and people are unchanged. Callers could then drop their configured Tenant id, which removes the deploy-time Tenant setting from every service in one GL change and lets a service act for any Tenant it is meant to serve. **Risk:** it removes the one per-request assertion that currently catches a caller's mistake. Today a stale cache, a wrong environment variable or a bug that supplies the wrong Company id becomes a 403, not a silent posting into another business's books; with Option A the header no longer guards a service that omits it, and the only remaining protection is the service's own correctness plus its credential, which authorizes it everywhere. It also quietly turns "this service serves one Tenant" from an enforced fact into a convention. **Mitigations if it is ever adopted:** scope each service principal to the Tenants (or Companies) it may act for, enforced in GL from the token or from a registry, so omitting the header still cannot cross Tenants; and audit every service-account posting (who, which Company), which GL cannot do yet because its audit trail has no writers. Without scoping, I would not recommend A.

## Option B: a read route that returns a Company's Tenant id

A new route such as `GET /companies/{companyId}` returning `{companyId, tenantId, name, baseCurrency, jurisdiction}`, readable by service accounts (no membership check, like the other service-callable reads) and by people with read access to that Company. A caller looks the Tenant up, caches it per Company, then sends the header as now. **Risk:** it discloses the Tenant id of any Company id to any service credential, and the Tenant id is exactly the value the header check compares against. A caller that wants to act on a Company need only ask GL, then echo the answer, so the header stops being an independent assertion and becomes a formality (A's weakness with an extra round trip), while every caller gains a new lookup, a cache and a failure mode. What B does keep is an explicit, loggable step, and people gain a read of the Company's own record. Tenant ids are identifiers, not secrets, so the disclosure is a design question rather than a leak, but it should be a deliberate decision.

## What GL recommends the SPUTO settle first

Neither option is safe until the SPUTO decides **what a service principal is allowed to act for**: one Tenant (today), a list of Tenants, or all Tenants; and whether that scope lives in the credential, in a registry, or in each service's configuration. With a scope enforced in GL, A becomes safe and B becomes unnecessary. Without it, A weakens tenancy and B only moves the lookup. Also for the SPUTO: the service-account membership bypass itself ("module-to-module calls are platform plumbing, EA's Membership model does not apply") is the second half of the same question, because it is what makes the header the only check. Related, already on the backlog: the GL audit trail has no writers (nothing records who posted), and re-tagging expense accounts and VAT changes have no audit trail.
