## 0. Review of Existing Code

As of 2026-08-11, `com.theprodeogroup.fish.domain.common` has 14 files sitting at the FiSH repo root (not yet in a `src/main/kotlin/...` folder structure, no Gradle project wraps them). What's there:

`audit_action.kt`, `client_type.kt`, `dimension_type.kt`, `export_format.kt`, `field_change.kt`, `journal_source.kt`, `order_by.kt`, `paginated_result.kt`, `period_status.kt`, `period_type.kt`, `posting_status.kt`, `request_context.kt`, `transaction_side.kt`, `validation_result.kt`.

**What's good, worth keeping the pattern of:**
- Every type has thorough KDoc — purpose, usage example, sometimes SQL hints. Keep this discipline; it's genuinely useful for a domain this compliance-heavy.
- `PostingStatus.canTransitionTo()` and `PeriodStatus.isValidTransition()` encode state-machine rules *inside* the value type rather than scattering `if` checks across services — good DDD tactical pattern, keep doing this for new state machines (e.g., `ArrearsCase` stage transitions, `EquityStake` status).
- `ValidationResult` with `success()/failure()/withWarnings()/combine()` is a clean Notification pattern — reuse it as the standard return type for domain validation, don't invent a second one.
- `PaginatedResult<T>` and `ExportFormat` are sensible generic/application-layer helpers, correctly kept out of any single aggregate.
- The `common` package itself — grouping small, related value objects/enums into one package rather than one file each — is the right call. **Do not** repeat the mistake from the abandoned prior attempt (47 files across nine packages for a domain this size). Split into a new package only when a cluster of types plus their behaviour becomes genuinely large (roughly 6–10+ files that belong together), not pre-emptively.

**Gaps to fix before/while building the core aggregates:**
1. ~~`field_change.kt` is **incomplete**~~ **Fixed (2026-08-11):** `FieldChange` now has `fieldName: String`, `oldValue: String?`, `newValue: String?`, `fieldType: String`.
2. **No `Ledger`-context aggregates exist yet** (Account, JournalEntry, Period) — `Tenant` (Tenancy context) is now built, see Section 9. Section 3.1 still defines what to build next for Ledger.
3. ~~**No package folder structure.**~~ **Fixed (2026-08-11):** files now live under `src/main/kotlin/com/theprodeogroup/fish/domain/common/`, matching their declared package. A Gradle project wraps them (`GL/build.gradle.kts`).
4. **No `Money` value object.** Nothing here represents an amount-plus-currency pairing. This is the single most important missing piece before `JournalLine` can be written correctly — see Section 3.1.
5. **Typed IDs started, not finished.** `TenantId`/`CompanyId`/`MembershipId` now exist as `@JvmInline value class` (`domain.tenancy.ids.kt`) — `AccountId`, `UserId`, etc. still need the same treatment when their aggregates are built. `RequestContext.clientId`/`userId` are still raw `java.util.UUID`.
6. ~~`PeriodStatus.isValidTransition(from)` reads backwards relative to `PostingStatus.canTransitionTo(newStatus)`~~ **Fixed (2026-08-11):** renamed to `canTransitionTo(newStatus)`, same calling convention as `PostingStatus`, when `Period` (Section 3.1) became the first real consumer of this enum.
7. **`RequestContext.sanitize()` is currently a no-op** — the comment says "nothing sensitive here," but `ipAddress` and `userAgent` are commonly PII under GDPR (Section 8.2 of the spec commits to GDPR/ICO compliance). ## 1. Ubiquitous Language

| Term | Meaning |
|---|---|
| Tenant | A customer organization using FiSH; the top-level data-isolation boundary. |
| Company | A legal entity within a Tenant. A Tenant may hold several Companies (group structure). |
| Client | A ledger party of a given `ClientType` (Individual, Sole Trader, Partnership, Company Limited, Non-Profit). Purse (credit union) uses `NON_PROFIT` — resolved 2026-08-11, see Section 8. |
| Account | A Chart-of-Accounts entry belonging to a Company: type (Asset/Liability/Equity/Revenue/Expense), code, parent/child hierarchy. |
| Journal Entry | A balanced, atomic set of debit/credit lines posted on a date. The core transactional unit of the ledger. |
| Journal Line | One debit or credit within a Journal Entry, referencing an Account, optionally tagged with `DimensionType` values. |
| Posting | The act of moving a Journal Entry from Draft/Pending to Posted, making it affect account balances and become immutable. |
| Period | A fiscal period (Month/Quarter/Year/Custom) belonging to a Company, with its own open/closed/locked lifecycle. |
| Money | An amount paired with a currency; never a bare number. |
| Audit Log Entry | An immutable record of an `AuditAction` against some entity, with `FieldChange` detail where applicable. |
| Loan Product | Purse-specific: a lending product with an APR ceiling and rate-breakdown components. |
| Arrears Case | Purse-specific: the staged (Early Contact → Pastoral Engagement → Formal Review → Final Resolution) record tracking a struggling loan. |
| Equity Stake | Purse/Scrip-specific: an ownership position arising from capitalizing a company's debt, held toward a turnaround. |
| Tax Rule / Tax Computation | Jurisdiction-specific configuration, and the derived tax-due record computed from a Company's posted ledger data. |

## 2. Bounded Contexts

FiSH is one platform but not one undifferentiated blob. Four bounded contexts, one core:

### 2.1 Ledger (core domain)
Double-entry bookkeeping: Chart of Accounts, Journal Entries, Periods, multi-currency, audit trail. This is FiSH's actual differentiator — everything else is built to make this trustworthy and reusable across ventures. Keep this context free of Purse-specific policy (no APR ceilings, no "common bond" fields *inside* Ledger aggregates) — those belong to the Lending context and reference Ledger concepts, not the other way around.

**Scope confirmed 2026-08-12, the user's own framing:** *"The GL Engine is the core engine of FiSH... It is built to handle the generic Financial Information of most companies. P and L, Balance Sheet, Working Capital Management, Bank Reconciliation."* Ties directly to the same day's Lending-separation resolution (below) — this is *why* the GL Engine has to stay generic: these four are what "any other organisation" needs, credit union or otherwise, independent of Lending's Purse-specific concerns.

- **P&L — built 2026-08-12** (`TrialBalance`/`ProfitAndLoss`, Section 3.1), derived entirely from `Account`/`JournalEntry` data already modeled, no new domain logic. **Balance Sheet** itself still isn't its own deliverable — a Balance Sheet is really just `TrialBalance`'s Asset/Liability/Equity lines presented as a statement (the Trial Balance already computes exactly those balances); whether it needs its own class or is just a different view/formatting of `TrialBalance`'s existing `lines` is undecided, not urgent since the underlying numbers already exist.
- **Working Capital Management — built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.WorkingCapital`, 7 passing tests, 173 total in the repo. Before building, checked the spec/business plans for a defined formula or threshold (the same discipline applied to `ArrearsCase`, Section 3.3) — **none exists anywhere**; the closest related material (Spec §7.14, Scrip's business-health signal) scopes that feed to revenue/expense and cash-flow trend only, not working-capital ratios. Confirmed scope given that gap: **the raw figure only** (`totalCurrentAssets - totalCurrentLiabilities`), not Current Ratio/Quick Ratio/Cash Conversion Cycle — `WorkingCapital.of(accounts, postedEntries, currency)` reuses the same `accountBalances()` helper as `TrialBalance`/`ProfitAndLoss`, filtering to Asset/Liability accounts whose `AccountClassification` (built for IAS 1, Section 3.1) is `CURRENT`. No new Money capability needed (Current Ratio was explicitly deferred — it would need Money-to-Money division, which doesn't exist; only scalar division does, added for Inventory costing). A point-in-time snapshot like `TrialBalance`, not scoped to a `Period`.
- **Bank Reconciliation — built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.BankReconciliation`, 9 passing tests, 182 total in the repo. Checked the spec/business plans first, same discipline as `ArrearsCase`/`WorkingCapital` — **no document defines a reconciliation workflow, matching tolerance, or outstanding-item mechanism**; the only related signal is the UK Business Plan naming Plaid (Open Banking) and ClearBank (Banking Rails) as future vendor infrastructure, not a spec'd import mechanism. Confirmed scope given that gap: **manual/explicit matching only** — `BankReconciliation.match(statementLineId, journalEntryId)` pairs a specific `BankStatementLine` (a plain external value the caller supplies — no import/ingestion layer exists anywhere in this codebase) with a specific posted `JournalEntry`, validating the entry has a line against the reconciled `accountId` on the expected side (via `CashDirection`, reusing `CashBookEntry`'s own "money in/money out" convention rather than raw `TransactionSide`) for the matching amount. No amount/date-tolerance auto-matching heuristic was invented. `isFullyReconciled` tracks match *completeness* (every statement line and every eligible posted entry matched), not a derived balance tie-out — `statementEndingBalance` is recorded but not enforced against anything, since no source material defines the adjustment math (deposits in transit, unpresented cheques) that real bank reconciliation reports typically show. `PostingStatus.hasHistoricalEffect()` (Section 2.1, added for `TrialBalance`) is reused here too, now `internal` rather than file-private, to filter which posted entries are eligible.

All four items in the GL Engine's confirmed reporting scope (P&L, Balance Sheet, Working Capital, Bank Reconciliation) are now built.

**IFRS grounding for Bank Reconciliation, confirmed 2026-08-12 — multiple standards plus audit expectations, not one:**
- **IAS 7** (Statement of Cash Flows) — accurate cash reporting, reconciling opening/closing balances. Already flagged as a gap in Working Capital's own grounding (Section 2.1 above, `project_working_capital_ifrs_grounding`) — no cash-and-equivalents classification or cash-flow statement exists; `BankReconciliation` is the *control*, not the IAS 7 report itself.
- **IAS 1** (Presentation) — cash must be complete/accurate/correctly classified, including overdrafts. `AccountClassification` (CURRENT/NON_CURRENT) is already built. **Overdraft reclassification built and tested 2026-08-12** — `TrialBalance.overdraftLines` (`domain.ledger`, 3 new tests, 247 total in the repo) flags Asset-type accounts with a negative balance, matching IAS 1's requirement that an overdrawn Cash account be *presented* as a Current Liability rather than a negative Asset. Deliberately a presentation-only flag — it doesn't touch `totalAssetAndExpense`/`totalLiabilityEquityRevenue`/`isBalanced`, which stay based on each Account's own `normalBalance()` type exactly as before (verified by a dedicated test). A future Balance Sheet view would use this to move flagged lines into the liability section when rendering.
- **IFRS 9** — bank accounts are financial assets; ECL/impairment for cash-like instruments isn't modeled (extends the same gap already flagged for trade receivables in Working Capital's grounding).
- **IAS 8** (Accounting Policies, Changes and Errors) — **new standard, not previously named in this doc.** Bank reconciliation is the practical mechanism that surfaces errors for IAS 8 to govern (correction, restatement) — `JournalEntry.reverse()` is the existing correction mechanism, but IAS 8's specific restatement rules aren't modeled against it.
- **ISA 315/330** — **worth a precise correction, not a nitpick:** these are International Standards on *Auditing* (IAASB), not IFRS/IAS accounting standards (IASB) — a different standards body entirely. The practical point still holds (a completed `BankReconciliation` is exactly the kind of evidence an auditor's existence/completeness testing would want), but it's an audit-evidence use case for the *output* of this feature, not a compliance target the domain model itself needs to satisfy.

**Correction to this pass's own build-order claim, not silently accepted:** *"Bank reconciliation will sit in the Period aggregate"* — it doesn't, and wasn't built that way. `BankReconciliation` is its own standalone aggregate in `domain.ledger`, with **no `PeriodId` field or dependency on `Period` at all** — it operates on an `AccountId` plus whatever `List<JournalEntry>` the caller supplies (any posted entry with a line against that Account, regardless of source — not specifically `CashBookEntry`-originated postings, though that's the common case). Matches every other reporting aggregate's shape (`TrialBalance`, `WorkingCapital`) more than it resembles `Period`.

**Also not built, despite this pass describing it as already accomplished:** "generate reconciling items (timing differences, errors)" and "produce audit-ready reconciliation reports" — `BankReconciliation` tracks `unmatchedStatementLines`/`unmatchedEntries` as plain lists, not categorized reconciling-item types (deposit-in-transit vs. bank error vs. timing difference), and has no report-formatting/output layer. The confirmed scope (see the build note above) was deliberately narrower than this.

**IFRS grounding for Working Capital, confirmed 2026-08-12 — no single standard, unlike AR/AP or Inventory; each component is governed separately, and this is where it maps onto what's already built vs. still missing:**
- **Inventory → IAS 2 + IFRS 15** — already documented, Section 2.6. No change here.
- **Trade Receivables → IFRS 15 + IFRS 9** — already documented, Section 2.5 (AR/AP timing). **Real gap surfaced by this pass:** IFRS 9's Expected Credit Loss (ECL) model — impairment on receivables expected to go uncollected — isn't modeled anywhere. `Customer.balance` (Section 2.5) is a raw running total with no provision/impairment concept. Not built, not previously flagged.
- **Trade Payables → IFRS 9** — already documented, Section 2.5. No change.
- **Cash & Cash Equivalents → IAS 7 — full requirement (reconciliation + Operating/Investing/Financing categorization) built 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.StatementOfCashFlows`, 261 total in the repo. `StatementOfCashFlows.of(cashAccount, postedEntries, startDate, endDate, currency)` reconciles `openingBalance`/`closingBalance`/`netCashFlow` as before (unchanged from the reconciliation-only build). **Categorization uses dimension tagging, not the earlier-rejected "derive from counter-account type" heuristic**: a new `DimensionType.CASH_FLOW_ACTIVITY` tag (`domain.common`) is applied directly to the cash/bank `JournalLine` itself, with the value being a `CashFlowActivity` (OPERATING/INVESTING/FINANCING, `domain.ledger`) enum name. Each posting method that touches cash was retrofitted to tag its own cash line, since it — not a generic account-type rule — is the only place that actually knows the transaction's economic substance: `Customer.receivePayment()`/`Creditor.makePayment()` → OPERATING (always, collecting a receivable or settling a payable), `FixedAsset.dispose()`'s proceeds line → INVESTING (always, regardless of the Revenue-typed `saleOfFixedAssetAccountId` counter-account that broke the old heuristic), `CashBookEntry` → a new `cashFlowActivity` constructor param defaulting to OPERATING (most day-to-day cash-book entries are routine operating movements; a caller recording a capital purchase or loan drawdown overrides it) — consistent with the confirmed non-accountant-friendly, forgiving-data-entry principle. `StatementOfCashFlows.activityAmounts: List<CashFlowActivityAmount>` holds the three buckets' signed net movements; any cash line with no tag (an older/legacy entry, or a posting method not yet retrofitted — Payroll/Prepayment don't touch cash directly today) falls into `uncategorizedAmount` rather than being dropped or crashing. `activityAmounts` plus `uncategorizedAmount` always sums to `netCashFlow`, verified by test. Only 4 methods needed retrofitting, not "every posting method" — most of what's built (`SalesOrder.deliverLine()`, `PurchaseOrder.send()`, `Payslip`, `Prepayment.recordRelease()`) doesn't touch a cash/bank Account directly at all.
- **Short-Term Borrowings → IFRS 9 + IAS 1 — built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.Borrowing`, 12 passing tests, 281 total in the repo. Models money the *Company itself* has borrowed (a bank loan, wholesale funding, an overdraft facility) — **not** the same concept as Section 2.9's Borrower/Lender Party-Role pair, which models Purse *lending to* members and is deferred to the separate Lending system; this is the mirror direction, ordinary corporate liability accounting every GL Engine tenant needs. `recordInterestAccrual(interestExpenseAccountId, accruedInterestPayableAccountId, periodId, date)` debits Interest Expense/credits Accrued Interest Payable for `outstandingPrincipal * annualInterestRate` — one call = one year's interest, same "callers decide their own cadence" discipline as `FixedAsset.recordDepreciation()`. `recordInterestPayment(...)` and `recordPrincipalRepayment(...)` settle each balance separately (capped at what's owed, mirroring `Creditor.makePayment()`/`Prepayment.recordRelease()`'s precedent), rather than one compound entry combining both — a real repayment often *does* bundle principal and interest into one bank transaction, but doing that in code would make a single cash line represent two different IAS 7 categories at once (principal repayment is Financing, interest paid is Operating), breaking `StatementOfCashFlows`'s categorization. `create()` doesn't post the initial drawdown, matching `FixedAsset`/`Prepayment`'s precedent that the originating cash movement (e.g. via `CashBookEntry`, tagged `CashFlowActivity.FINANCING`) is a separate concern. IAS 1's current/non-current split needs no new code — `WorkingCapital` already reads it generically off whatever `AccountClassification` the caller assigns the Loan Payable account.
- **Prepayments → IAS 1 + IFRS 15 — built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.Prepayment`, 6 passing tests, 244 total in the repo. Deliberately mirrors `FixedAsset`'s straight-line shape almost exactly (`amount`/`amountReleased`/`remainingBalance` corresponds to cost/accumulated depreciation/net book value; `numberOfPeriods` corresponds to `usefulLifeYears`). `recordRelease(expenseAccountId, prepaidAssetAccountId, periodId, date)` debits expense, credits the prepaid asset, using `JournalSource.SYSTEM`, capped at `remainingBalance` with the same rounding-remainder-capture behavior as `FixedAsset.recordDepreciation()`. One call = one period's release, not a calendar-date proration — same "callers decide their own cadence" discipline. Returns `null` once fully released.
- **Accrued Expenses → IAS 1 + IFRS 9 — built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.AccruedExpense`, 8 passing tests, 269 total in the repo. Confirmed before building: the underlying accounting mechanic (post an estimate, reverse it next period, post the real invoice normally) was already fully supported — `JournalEntry.reverse()` plus `JournalSource.SYSTEM`'s own doc comment ("Automatic accruals") already covered it, so this doesn't replace that mechanic. What it adds is **queryable state**: `isPosted`/`isReversed`/`isOutstanding` let a caller find which accruals are still awaiting reversal, something a raw `List<JournalEntry>` can't answer since nothing on `JournalEntry` marks an entry as having been an accrual in the first place. `postAccrual(expenseAccountId, accruedLiabilityAccountId, periodId, date)` debits Expense/credits Accrued Liability for the full amount (`JournalSource.SYSTEM`); `reverseAccrual(...)` posts the mirror-image lines (`JournalSource.REVERSAL`, matching `JournalEntry.reverse()`'s own convention) — each builds its own lines directly rather than calling `.reverse()` on a stored entry, since no aggregate in this codebase holds another aggregate's object, only ever returns one. Structurally the **mirror image of `Prepayment` in direction, not in shape**: Prepayment is cash paid now / expense recognized progressively later (an asset released over many periods via repeated `recordRelease()`); AccruedExpense is expense recognized now / cash paid later (a liability settled by a single reversal, so `postAccrual()`/`reverseAccrual()` are two one-time actions, not a multi-period schedule).
- **Provisions (uncertain-amount/timing liabilities) → IAS 37 — built and tested 2026-08-12, on explicit request, not part of this pass's original gap list.** `com.theprodeogroup.fish.domain.ledger.Provision`, 10 passing tests, 291 total in the repo. **Genuinely distinct from `AccruedExpense`, not a variant of it**: an accrual is a reasonably certain amount just not yet invoiced, while a Provision exists because the amount and/or timing is uncertain and must be estimated, then reviewed. IAS 37's three recognition criteria (present obligation, probable outflow, reliable estimate) are a caller-side judgment call, not evaluated by this type — same "data, not code" treatment as `TaxRule`/ECL loss rates. `remeasure(targetAmount, expenseAccountId, provisionAccountId, periodId, date)` deliberately mirrors `Customer.assessExpectedCreditLoss()`'s target-and-delta shape (re-assess to a target each call, post only the difference, `JournalSource.SYSTEM`) rather than `FixedAsset.recordDepreciation()`'s pure accumulation, since a provision must be able to shrink or fully reverse if the obligation is no longer probable. `utilize(amount, cashAccountId, provisionAccountId, periodId, date)` settles the provision when the obligation crystallizes (`JournalSource.MANUAL`, capped at balance, cash line tagged `CashFlowActivity.OPERATING`) — IAS 37's "restricted use" rule (an expenditure may only be charged against the provision it relates to) holds structurally, since `utilize()` only ever reduces *this* Provision instance's own balance, never a shared pool. **Deliberately does not discount to present value** — IAS 37 requires discounting when the time value of money is material (typically long-term provisions), which would need an unwinding-of-discount finance-cost line each period; no source doc defines a discount rate methodology, so `balance` is assumed to already be whatever amount the caller wants recognized (pre-discounted by the caller, if that applies).
- **Correction to one claim in this pass's own summary:** `ArrearsCase` (Section 3.3) does **not** govern "short-term liabilities" — it governs the **Borrower** role (Section 2.9), an **IFRS 9 financial *asset*** (a loan receivable Purse is owed), not a liability. The role that actually maps to short-term borrowings/liabilities is **Lender** (Section 2.9's mirror-image role — a counterparty who lends *to* Purse, e.g. member deposits or wholesale funding), which has no built aggregate at all yet. Don't conflate the two, matching Section 2.9's own explicit Borrower-vs-Lender distinction.
- **The Party-Role mapping (Section 2.9) does hold up**, corrected as above: Customer→IFRS 15, Supplier/Creditor→IFRS 9, Staff→IAS 19, Borrower→IFRS 9 (asset), Lender→IFRS 9 (liability) — all design-only except Creditor/Customer (built).

**Confirmed 2026-08-11: FiSH is accrual-based accounting**, not cash-basis — **grounded specifically in IAS 1** (Presentation of Financial Statements — IAS 1.27 requires the accrual basis), not just a general engineering preference. Financial facts are recognized when incurred/earned, not when cash actually moves. Concretely, and **asymmetric between the two sides by deliberate design, each grounded in a different standard** (see Section 2.5's final, confirmed timing model): `Accounts Payable` is recognized in full when a Purchase Order is *sent* ("when we order we owe"), per **IFRS 9**'s financial-liability recognition (a present obligation to repay cash or another financial asset), while Income/`Accounts Receivable` is recognized progressively *as a Sales Order is delivered*, per **IFRS 15**'s performance-obligation model (income recognized when earned, i.e. when the obligation is satisfied) — not when the sale is placed. Both are accrual (neither waits for cash to move), but they're governed by two different standards, which is exactly why they don't share a recognition trigger. Worth checking against this principle, asymmetry included, whenever a new module's posting timing gets designed (Payroll accruing unpaid wages, Inventory/COGS timing, etc.) rather than assuming symmetric timing by default.

**This forward-looking checklist item — "Payroll accruing unpaid wages" — is now built, alongside three siblings, all 2026-08-12, all direct instances of the same accrual principle applied to cases beyond the original AP/AR asymmetry:**
- `AccruedExpense` (IAS 1 + IFRS 9) — a reasonably certain cost incurred but not yet invoiced, recognized when incurred, not when the invoice arrives or cash moves. The most literal instance of the principle.
- `Borrowing` (IAS 1 + IFRS 9) — interest recognized as it accrues on outstanding principal (`recordInterestAccrual()`), independent of when it's actually paid (`recordInterestPayment()`) — the same obligation-based timing IFRS 9 already grounds AP recognition in, applied to a different liability.
- `Provision` (IAS 37) — the accrual principle's edge case: recognized even when the *amount itself* is uncertain, as long as the obligation, probability, and a reliable estimate exist. Confirms the principle isn't "record it once you know the exact number," it's "record it once the obligation exists and can be reasonably estimated."
- `LeaveAccrual` (IAS 19, `domain.payroll`) — resolves the checklist item by name: unpaid leave entitlement accrued as the employee earns it (a `Provision` wrapper), not when the leave is taken or paid. Bonus/profit-share accruals (also IAS 19) reuse `AccruedExpense` directly; non-accumulating absences are the principle's own boundary case — IAS 19.13 says rendering service does *not* increase that benefit, so *nothing* accrues, consistent with "recognize when incurred," since nothing is incurred until the absence happens.

All four follow the same recognize-the-obligation-not-the-cash-movement logic already established for AP/AR — no new principle needed, just wider application. **Framing confirmed and sharpened by the user (2026-08-11):** the GL's job is for a Company to "recognise its own income, expenditure, capital, assets and liabilities" — a plain-language restatement of `Account`'s five types (Revenue/Expense/Equity/Asset/Liability, Section 3.1). Sharpened further, same session: **"The GL sole purpose is the financial effect."** Not a soft emphasis — a hard scope boundary. The GL records the financial *effect* of activity (postings, balances) and nothing about the operational/member detail that produced it (loan terms, order details, member records) — that detail belongs to whichever context generated it (Lending, and eventually Purchase/Sales Order Processing, Section 2.5) and posts its financial effect into Ledger. This is a general principle, not Purse-specific — applies the same way to any Company FiSH serves, credit union or ordinary SMB client.

### 2.5 Purchase Order Processing / Sales Order Processing (both cores built 2026-08-11; Inventory Management/Payroll still design-only)

Restated and sharpened the same day: **"This is the generic ecosystem for a GL engine."** Not four independent bolt-ons — an *ecosystem*, i.e., these four (PO/SO Processing, Payroll, Inventory Management — see 2.6/2.7) are expected to be interconnected (goods/AR/AP/payroll all post into the same Ledger, and 2.6 already flags PO/SO/Inventory as one connected cluster) and together constitute what makes a GL engine generic across different types of companies — not Purse-specific add-ons, but the standard cross-industry toolkit that fulfills the spec's own stated ambition of a general-purpose B2B ledger (spec §2, "supports the general-purpose client types... this generality is already a design decision, not an open question"). Purse needs Lending on top of this ecosystem; an ordinary SMB client mostly just needs the ecosystem itself.

Inventory Management and Payroll are still not designed at field/aggregate level — Purchase Order Processing's and Sales Order Processing's cores now are (see below), Increments 1 and 2 of the ecosystem build, matching the roadmap's own ordering (PO first: simpler, no progressive-recognition complexity; SO second, mirroring PO's structure with the added asymmetric timing). What's confirmed for all of them: these are what will keep AR/AP accurate against the GL, for both ongoing operations and a Company's opening/historical figures at onboarding (Section 9.8) — the same mechanism handles both, rather than onboarding needing its own bespoke AR/AP import path.

**Mapping confirmed 2026-08-11** (the earlier working assumption was right):
- **Sales Order Processing** → creates **Customers** and, where the sale is on credit, **Accounts Receivable** — the counterparty is a **Debtor** once there's a balance owed. "Debtor" is the standard UK/Commonwealth accounting term (matches British English throughout the spec and Purse's UK context), same relationship as "Trade Debtors" on a UK balance sheet.

**Confirmed 2026-08-11 — the two-layer reading above is correct.** The user's own framing: "only customers with outstanding payments need to be registered in the books" — i.e., *registration in the books* (a Debtor record) is driven by having a balance, not by the sale happening at all. Not every Customer is a Debtor at a given moment; every Debtor is a Customer.

**New, optional, explicitly deferred:** cash customers (who never carry a balance, so never need Debtor registration for GL accuracy) may *optionally* — and the user recommends this — still be registered as Customers anyway, for marketing purposes, "possibly through a loyalty scheme." **Confirmed 2026-08-12, closing a gap that was implicit but never written down: which mechanism actually posts a cash sale.** The user's own framing: *"Cash sales dr Cash book Cr Sales / Sales on Credit must Dr Customer Account/Accounts Receivable Cr Sales."* Both rules are already correctly implemented in this codebase, via two separate, purpose-built mechanisms that had never been explicitly cross-referenced as *the* answer to this question:
- **Cash sales → `CashBookEntry`** (Section 3.1), not `SalesOrder` at all. `CashBookEntry(cashAccountId, CashDirection.RECEIVED, amount, salesRevenueAccountId, date).toJournalEntry()` produces exactly `Dr cashAccountId / Cr salesRevenueAccountId` — no `Customer`/AR involvement, because none is needed.
- **Credit sales → `SalesOrder.deliverLine()`** (above), which debits the AR control account (now tagged `DimensionType.CUSTOMER`, 2026-08-12) and calls `customer.recordSale()`.
- **`SalesOrder` was never meant to handle cash sales** — this section's own opening line already scoped it that way ("Sales Order Processing → creates Customers and, **where the sale is on credit**, Accounts Receivable"), it just was never stated as the reason `CashBookEntry` exists as a separate mechanism rather than a case `SalesOrder` needs to branch on. No code changed here — this closes a documentation gap, not a functional one.

**Control account architecture, resolved 2026-08-11 — this settles the "onboarding snapshot vs. ongoing subledger" question left open above and in Section 9.8.** This point went through several rounds of correction in conversation before landing — see `project_future_modules` in memory for the revision history if it matters later. **What follows is the final, explicitly confirmed model — treat it as current, not any earlier draft of it.**

- `Accounts Payable` and `Accounts Receivable` are each a **control account** in core Ledger — a single `Account` (Liability / Asset type respectively) in the Company's Chart of Accounts representing the *total* owed to suppliers / owed by customers.
- Each individual counterparty's balance lives in a **subsidiary ledger** — Creditor balances owned by Purchase Order Processing, Debtor balances owned by Sales Order Processing (per Section 2.1's scope boundary — the module owns the counterparty-level detail, Ledger only holds the control account's aggregate effect).
- **The control account must always tally with the sum of subsidiary balances** — the actual mechanism, not a soft goal. It's *why* AR/AP can't be a one-time onboarding snapshot: a control account only means anything if the subsidiary ledger is tracked continuously and reconciles against it. This is what resolves the "snapshot vs. subledger" question (Section 9.8/`project_anchor_date_onboarding`) as genuinely settled: itemized AR/AP is an ongoing subledger.
- **Recognition timing is asymmetric between the two sides, confirmed 2026-08-11 — this is the final answer after two earlier drafts got corrected:**
  - **Purchase Order Processing (AP):** "When we order we owe" — the user's own words. AP is recognized **when the Purchase Order is sent**, in full, not progressively as goods arrive (an intermediate draft tried progressive recognition here and was explicitly reverted). Credit `Accounts Payable` (control) and the supplier's subsidiary account at PO-send; debit both, credit Cash/Bank, when paid.
  - **Sales Order Processing (Income/AR):** "When they order, Income is recognised as we deliver" — the user's own words. Placing a Sales Order does **not** recognize income. Income/`Accounts Receivable` accrues **progressively as the order is fulfilled/delivered** — the reverse timing from AP, not the same timing mirrored.
  - **Grounded in specific IFRS/IAS standards, per the user (2026-08-11), not just convention:**
    - **IFRS 15** (Revenue from Contracts with Customers) uses a five-step model; the relevant one here is **Step 5**: revenue is recognized when (or as) control of goods/services transfers to the customer, regardless of cash timing. Two sub-cases matter for Sales Order Processing specifically: a **point-in-time** transfer (a physical product delivered — recognize revenue at that point) vs. an **over-time** transfer (a service delivered across a period — recognize revenue progressively as it's delivered, not just at the very end). Both are "income recognized as delivered," but which sub-case applies depends on whether a given Sales Order is a goods sale or a service.
    - **IFRS 9** (Financial Instruments): a financial liability is recognized "when the entity becomes party to a contractual obligation to deliver cash or another financial asset" — initially at fair value, at the point the contract is signed/the obligation arises. FiSH treats sending a Purchase Order as that point, ahead of goods receipt.
    - **IAS 1** (Presentation of Financial Statements): IAS 1.27 is the general basis requiring accrual accounting at all — the standard underlying the broader "FiSH is accrual-based" principle in Section 2.1. IAS 1 also governs **current vs. non-current classification** of a recognized liability (see the new `Account` requirement in Section 3.1) — a liability is current unless the Company has the unconditional right to defer settlement ≥12 months, and covenant breaches can force otherwise-non-current debt into current classification (repayable on demand).
    - **Practical summary, the user's own framing:** revenue is *earned-based*, debt is *obligation-based*. Neither depends on cash movement — both depend on the underlying economic event, just different events (satisfying a performance obligation vs. incurring a contractual obligation). That's precisely why they aren't symmetric even though the control-account mechanism is.
    - This isn't a from-scratch design choice or an informal "prudence" convention — it's the two sides of AR/AP being governed by two different standards (a revenue-recognition standard vs. a financial-instruments standard), which is exactly why they don't share a recognition trigger even though the control-account mechanism is otherwise symmetric.
  - **The control-account *structure* still mirrors exactly between AP and AR** (control account + subsidiary ledger + tally) — only the *recognition trigger* differs. "Mirror image," the user's earlier description of Sales vs. Purchase Order Processing, refers to the structure, not the timing.
- **Correction confirmed 2026-08-11:** the original Purchase Order example named "Accounts Receivable" — confirmed a label slip for Accounts Payable, the buying/owing side.
- **Event ordering:** "we buy, we owe" is confirmed atomic again (AP recognized fully at order time) — receiving goods and paying can still happen in either order relative to each other, without affecting the AP amount already recognized at PO-send; since the full liability exists from PO-send onward, a prepayment before goods arrive simply debits the same AP balance, no separate handling needed. On the Sales side, income timing tracks delivery instead, independent of when the customer's payment arrives.

This surfaces two candidate entities: **Customer** and **Creditor** (AR/AP counterparties). `DimensionType.CUSTOMER`/`VENDOR` already exist in `domain.common` as journal-line tags, which presumes *something* with an ID sits behind them — but a tag value isn't the same as a first-class entity with its own record. **Resolved for both, built 2026-08-11:** both are real aggregates, not reference-only concepts — see below, `Customer` mirrors `Creditor`'s shape exactly. Still depends on Ledger the same way Lending and Tax do (post through it, don't get absorbed into it).

**Purchase Order Processing, Increment 1 — built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.purchasing` (`Creditor`, `PurchaseOrder`, `PurchaseOrderLine`, `PurchaseOrderStatus`), 13 passing tests (6 `Creditor`, 7 `PurchaseOrder`). Deliberately scoped to just what recognizes AP — goods-receipt/fulfillment tracking (the eventual Inventory Management linkage), cancellation, and payment-application-to-specific-orders are **not** built yet, left for later increments.

- **`Creditor`** — `id`, `companyId`, `name`, `currency`, and a `balance: Money` it tracks itself (private-set, mutated only via `recordCharge()`/`recordPayment()`) — this **is** the subsidiary ledger in code, not a derived/computed view. Registration is unconditional (unlike the Debtor-side "only customers with a balance get registered" rule above) — creditors don't have the cash-supplier/loyalty-scheme asymmetry that motivates that rule for Debtors.
- **`PurchaseOrder`** — `id`, `companyId`, `creditorId`, `date`, `lines: List<PurchaseOrderLine>` (each: `description`, `accountId` — the expense/asset `Account` being debited, `amount: Money`; no quantity/unit-price/tax breakdown in this increment). `PurchaseOrderStatus` is a minimal `DRAFT`/`SENT` enum — no richer lifecycle built yet.
- **`send(creditor, apControlAccountId, periodId)`** is the concrete implementation of the control-account mechanism (above): debits every line's `Account`, credits `apControlAccountId` for the order total (one control-account line, not one per order line), and calls `creditor.recordCharge(total)` in the same call — control account and subsidiary ledger move together by construction. Matches "when we order we owe": the full amount posts at send time, not progressively. Returns `JournalEntry?` — `null` if the order isn't `Draft` or the passed `Creditor` doesn't match `creditorId`, matching `JournalEntry.reverse()`'s precedent for a method that produces a new object on success rather than just mutating `this`.
- **Fixed 2026-08-12 — the AP control line now carries `DimensionType.VENDOR`.** A real gap, not previously flagged: `JournalLine.dimensions` (Section 3.1) existed specifically for this purpose but was never actually populated anywhere in the codebase — the Ledger had no record of which `Creditor` a posting belonged to, only `Creditor.balance`'s own running total did (and that total, once updated, discards which order/date produced it). Tagging the control line with `DimensionType.VENDOR -> creditorId` means aging/reporting can now be derived directly from already-posted `JournalEntry` data (each entry already has a `date`) instead of needing `Creditor` to redundantly track its own transaction history — the same pattern `TrialBalance`/`WorkingCapital` already use (derive from Ledger, don't duplicate state). `SalesOrder.deliverLine()` got the mirror fix, tagging its AR line with `DimensionType.CUSTOMER`. This directly unblocks any future aging-based Expected Credit Loss work (flagged as a gap in Working Capital's IFRS grounding above) without needing to retrofit `Customer`/`Creditor` themselves.
- **`Money` gained a `minus` operator** — needed for `Creditor.recordPayment()` to decrease balance; wasn't required until a real running balance needed both directions.
- **Amount validation (positive-only, same pattern as `CashBookEntry`)** applies to `Customer.recordSale`/`recordReceipt` too (below) — the question of whether this holds once partial payments or credit notes exist is still open, not a problem yet since only whole-line charges exist so far.

**`Creditor.makePayment()` and `AccountsPayableAging` — built and tested 2026-08-12**, the AP mirror of the AR receivable-payment/aging work below. `Creditor.recordPayment()` had the identical orphan-method gap `Customer.recordReceipt()` did — no caller anywhere posted the offsetting `JournalEntry`. Fixed with `Creditor.makePayment(amount, cashAccountId, apControlAccountId, periodId, date)`: debit the AP control account (tagged `DimensionType.VENDOR`), credit Cash — the mirror image of `Customer.receivePayment()`'s debit-Cash/credit-AR. `AccountsPayableAging.of(creditorId, apControlAccountId, postedEntries, asOfDate, currency)` (`com.theprodeogroup.fish.domain.purchasing`) buckets outstanding payables the same way `AccountsReceivableAging` does, but with debit/credit **swapped, not copy-pasted by mistake**: a charge (`PurchaseOrder.send()`) *credits* the AP control account (a liability increasing), a payment *debits* it — the exact mirror of AR, where a sale debits and a receipt credits. Same FIFO/oldest-first allocation caveat. **No ECL-equivalent was built for `Creditor`** — Expected Credit Loss is specifically an IFRS 9 concept for financial *assets* at risk of non-collection; there's no accounting equivalent for a liability you owe, so this increment is aging-only, not a full AP mirror of the AR increment. `AgingBucketLabel`/`AgingBucketAmount` were relocated from `domain.sales` to `domain.ledger` as part of this — they're generic data shapes, not sales-specific, and `domain.purchasing` needed them without reaching into `domain.sales`. 10 new tests (2 `Creditor`, 8 `AccountsPayableAging`), 233 total in the repo.

**Sales Order Processing, Increment 2 — built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.sales` (`Customer`, `SalesOrder`, `SalesOrderLine`, `SalesOrderStatus`), 15 passing tests (6 `Customer`, 9 `SalesOrder`). Mirrors Purchase Order Processing's control-account structure exactly, but the recognition timing is asymmetric by design (Section 2.1/2.5 above) — placing a `SalesOrder` recognizes nothing; income is recognized progressively as delivery happens.

- **`Customer`** — identical shape to `Creditor` (`id`, `companyId`, `name`, `currency`, self-tracked `balance: Money`), `recordSale()`/`recordReceipt()` instead of `recordCharge()`/`recordPayment()`. Registration is unconditional here too, same reasoning as `Creditor`.
- **`SalesOrder.status` is computed, not stored/transitioned** — `DRAFT`/`PARTIALLY_DELIVERED`/`FULFILLED`, derived from how many lines have been delivered so far, rather than mutated through a `canTransitionTo()`-style state machine like every other status enum in this codebase. There's no single moment (unlike `PurchaseOrder.send()`) that changes everything at once, so a transition table didn't fit the shape of the problem.
- **`deliverLine(lineIndex, customer, arControlAccountId, periodId)`** recognizes *one line's* worth of income per call, not an arbitrary partial amount — debits the AR control account for that line's amount, credits that line's own revenue `Account`, and calls `customer.recordSale()` in the same call. **Why per-line rather than a proportional split across a partial Money amount:** genuinely progressive/staged recognition (multiple deliveries over time) needs *some* way to say "this much has been recognized so far" — per-line delivery gives that without needing `Money` multiplication/division or a proportional-allocation scheme across a multi-line order, neither of which has been requested. A caller delivering a whole multi-line order at once just calls this once per line. Returns `JournalEntry?`, `null` on invalid line index, already-delivered, or a mismatched `Customer` — same precedent as `PurchaseOrder.send()`/`JournalEntry.reverse()`. **Fixed 2026-08-12: the AR line now carries `DimensionType.CUSTOMER -> customerId`** — see the matching `PurchaseOrder.send()` note above; the same previously-unpopulated-dimensions gap existed on this side too, fixed the same way.
- **Deliberately deferred, matching Increment 1's discipline:** goods-receipt/Inventory linkage (what triggers a line being "deliverable"), cancellation, and payment-application-to-specific-orders are not built. The point-in-time vs. over-time (IFRS 15) distinction between physical-goods and service lines also isn't modeled — every line is treated the same way (recognized in full when `deliverLine()` is called for it), which happens to match the point-in-time case but doesn't yet support true over-time/percentage-of-completion recognition within a single line.

**Receivable payments, aging, and Expected Credit Loss — built and tested 2026-08-12.** Three connected fixes/additions, all driven by the user working through why `Customer.balance` alone couldn't support IFRS 9's ECL model (Section 2.1's flagged gap):

1. **`Customer.receivePayment(amount, cashAccountId, arControlAccountId, periodId, date)` — a real bug fix, not a new feature.** `Customer.recordReceipt()` (and `Creditor.recordPayment()`, same gap on the AP side) existed with no caller anywhere that actually posted the offsetting `JournalEntry` — a payment updated `balance` but left no trace in the Ledger. Fixed by combining `recordReceipt()` with a `JournalEntry` (debit Cash, credit AR — the AR line tagged `DimensionType.CUSTOMER`, same as the sale side), matching `SalesOrder.deliverLine()`'s "control account and subsidiary ledger move together by construction" pattern. Returns `JournalEntry?`, `null` on a non-positive amount.
2. **`AccountsReceivableAging.of(customerId, arControlAccountId, postedEntries, asOfDate, currency)` (new file, `domain.sales`)** — buckets a Customer's outstanding receivables by age (`CURRENT` 0-30 days, `DAYS_31_TO_60`, `DAYS_61_TO_90`, `OVER_90`), derived entirely from already-posted `JournalEntry` data via the `DimensionType.CUSTOMER` tag (2026-08-12's other fix, above) — a query/report layer, same shape as `TrialBalance`/`WorkingCapital`, no new domain state. **FIFO/oldest-first allocation, not per-invoice cash application**: nothing in this codebase ties a specific receipt to a specific sale (`Customer.balance` is "balance forward," not "open item"), so receipts are summed and applied against the oldest unpaid sales first — the standard simplification for balance-forward AR systems, not a stored fact. Aging is measured from the *sale* date, not a due date — no credit-terms/payment-terms concept exists anywhere yet.
3. **`Customer.assessExpectedCreditLoss(aging, lossRates, expenseAccountId, allowanceAccountId, periodId, date)`** — IFRS 9's simplified approach for trade receivables (always lifetime ECL via a provision matrix, not the full 3-stage general model — the standard, expected treatment for trade receivables specifically, not a judgment call). `lossRates: Map<AgingBucketLabel, BigDecimal>` is "data, not code," same treatment as `TaxRule`/`PayrollDeductionLine`; a bucket missing a rate defaults to zero rather than failing. **Re-assesses to a target each call, unlike `FixedAsset.recordDepreciation()`'s pure accumulation** — ECL isn't a period cost that only grows, so if the balance shrinks or rates improve, the allowance should move down too. Posts only the *delta* between the new target and the current `allowanceForExpectedCreditLoss` (a new self-tracked contra-asset field, private-set): a top-up (debit expense/credit allowance) if the target rose, a reversal (debit allowance/credit expense) if it fell. The target is capped at `balance` — never provision more than what's actually owed. Uses `JournalSource.SYSTEM`. `Customer.netReceivable = balance - allowanceForExpectedCreditLoss` is the new computed property a Balance Sheet would actually want to show. Returns `null` if `aging.customerId` doesn't match, or if the delta is exactly zero.

15 new tests (7 `Customer`, 8 `AccountsReceivableAging`), 215 total in the repo.

### 2.6 Inventory Management (core built 2026-08-11 — Increment 3)

Named by the user 2026-08-11, alongside Purchase/Sales Order Processing — part of the same "current build scope" upgrade as 2.5. `com.theprodeogroup.fish.domain.inventory` — **`StockItem`** (`id`, `companyId`, `name`, `currency`, self-tracked `quantityOnHand: BigDecimal` and `unitCost: Money`, both private-set; computed `totalValue = unitCost * quantityOnHand`). `Money` gained `times(BigDecimal)`/`div(BigDecimal)` scalar operators for this (`div` uses `MathContext(34)` before `Money`'s own minor-unit rounding, so non-terminating divisions like 10.00/3 round rather than throwing).

Returns `null` if the `StockItem` is missing, doesn't match the line's `stockItemId`, or there isn't enough stock to issue.

**IFRS grounding, confirmed 2026-08-12 — two standards, not one, matching the AR/AP pattern in Section 2.1/2.5 ([[project_accrual_accounting_basis]]):**
- **IAS 2 (Inventories)** governs inventory *while held* — measurement (lower of cost and net realisable value, NRV), the permitted cost formulas (FIFO or weighted-average; **LIFO is prohibited**), recognition, write-downs and their reversal, and WIP/manufacturing overhead treatment. `StockItem`'s weighted-average choice is IAS 2-compliant by construction (one of exactly two permitted formulas).
- **IFRS 15 (Revenue from Contracts with Customers)** governs *derecognition* — inventory leaves the books and becomes Cost of Sales at the same moment control transfers to the customer, i.e. the same trigger already used for `SalesOrder.deliverLine()`'s income recognition (Section 2.5). This is the concrete shape the deferred "goods-shipped-against-SO decreases it and posts COGS" linkage will take once built: one event, two postings (revenue via `deliverLine`, COGS via `StockItem`).
- **Corrected 2026-08-12, later the same day this grounding was first written:** the second gap originally listed here — "no COGS posting exists anywhere yet" — is stale. COGS posting was built the same day (see "Live PO/SO linkage," directly above this note): `SalesOrder.deliverLine()` posts COGS as part of its compound entry. Don't recall that as a current gap.
- **Lower-of-cost-and-NRV write-down — built and tested 2026-08-14, closing the last item from the original Inventory grounding.** `StockItem.assessNetRealisableValue()`, 8 passing tests, 326 total in the repo. `nrvWriteDownPerUnit` is a *separate* contra-value, same relationship `FixedAsset.accumulatedDepreciation` has to `cost` — `unitCost`/`totalValue` stay pure historical weighted-average cost, unaffected, still the correct basis for the next `recordReceipt()`'s blend; `carryingValuePerUnit`/`totalCarryingValue` (new computed properties) are the derived lower-of-cost-and-NRV figures a Balance Sheet actually needs. Tracked per-unit, not as a running total, specifically so `recordIssue()` never needs to touch it — the same reason `unitCost` itself is per-unit. Deliberately mirrors `Customer.assessExpectedCreditLoss()`'s target-and-delta shape (re-assess to a target each call, post only the difference) rather than `FixedAsset.recordDepreciation()`'s pure accumulation, since IAS 2.34 explicitly requires reversals when NRV recovers — capped so the reversal never exceeds the original write-down (inventory is never carried above its own cost), which falls out naturally from the target always being `max(0, unitCost − NRV)`.
- Supporting/indirect standards, lower priority: **IAS 23** (borrowing costs may be capitalised into inventory cost only for goods needing a substantial period to get ready — e.g. long-maturation goods, not typical fast-moving stock), **IAS 36** (impairment for assets outside IAS 2's own NRV mechanism), **IAS 1** (balance-sheet presentation/current-asset classification — already partially covered by `AccountClassification`, Section 3.1).

**Manufacturing accounting's full IFRS grounding, provided 2026-08-12 alongside the confirmed three-stage Manufacturing/Trading/P&L structure (Section 3.1's `ExpenseClassification` note) — a fuller map than the summary above, worth recording in full since it surfaces real gaps beyond WIP and NRV:**
- **IAS 2 stays the backbone**, as above — cost components (materials/labour/overhead), overhead allocation (fixed overhead by *normal* capacity, variable overhead by *actual* production — a genuinely new, unbuilt computation, not equivalent to just tagging an Account `FACTORY_OVERHEAD`), abnormal waste (expensed, never capitalised into WIP/inventory cost), WIP measured at cost-to-date, finished goods at cost until sold, NRV write-downs (the gap already flagged above).
- **IAS 16 (PPE) — confirmed already achievable with zero new code, a real win from the `ExpenseClassification` design choice.** Manufacturing machinery depreciation should flow into the factory overhead pool. Checked `FixedAsset.recordDepreciation(depreciationExpenseAccountId, ...)`: it already takes a plain caller-supplied `AccountId` - since `expenseClassification` lives on the `Account` itself (not on the posting method), a caller can already point `depreciationExpenseAccountId` at an Account tagged `FACTORY_OVERHEAD` today. Nothing to build here.
- **IAS 23 (Borrowing Costs) — built and tested 2026-08-14, distinct from the inventory-cost capitalisation already noted above.** `Borrowing.capitaliseInterest()`, 3 passing tests, 329 total in the repo. Scope confirmed before building — deliberately does **not** implement IAS 23's commencement/suspension/cessation state machine or the specific-vs-general-borrowings weighted-average capitalisation rate, both real complexity in the full standard. `capitaliseInterest()` mirrors `recordInterestAccrual()`'s exact interest computation (`outstandingPrincipal * annualInterestRate`, one call = one year) and its effect on `accruedInterestPayable` - the liability owed to the lender is identical either way. Only the debit side differs: a caller-supplied `qualifyingAssetAccountId` (an asset under construction) instead of an Expense account. The caller decides entirely when capitalisation should apply, by choosing which method to call for a given period - not both, for the same interest charge.
- **IFRS 15 — already correctly modelled**, as above (COGS derecognition at the point control transfers, same trigger as `SalesOrder.deliverLine()`'s income recognition). No change.
- **IAS 1 — already partially covered**, as above (`AccountClassification`). Disclosure of inventory accounting policy/overhead allocation method is a reporting/notes-output concern, not built - matches the broader "no application/reporting output layer exists yet" gap.
- **IAS 36 (Impairment) — built and tested 2026-08-14, closing this section's last manufacturing IFRS gap.** `FixedAsset.assessImpairment()`, 7 passing tests, 336 total in the repo. Distinct from IAS 2's NRV test (inventory-specific); this is the recoverable-amount test for manufacturing *assets* (factory machinery, production lines). `accumulatedImpairmentLoss` is a *second* contra-value alongside `accumulatedDepreciation` - the critical design point is that `netBookValue` deliberately stays exactly `cost − accumulatedDepreciation`, **never** reduced by impairment, so it keeps meaning "what this asset would be carried at had no impairment ever been recognised" — IAS 36.117's own reversal ceiling, achieved for free rather than tracking a separate hypothetical depreciation schedule. `carryingAmount` (`netBookValue − accumulatedImpairmentLoss`) is the actual Balance Sheet figure. `assessImpairment(recoverableAmount, ...)` mirrors `Customer.assessExpectedCreditLoss()`/`StockItem.assessNetRealisableValue()`'s target-and-delta shape (target = `max(0, netBookValue − recoverableAmount)`, posts only the difference), so a reversal can never push `carryingAmount` above `netBookValue`. `dispose()` gained a fourth, optional clearing leg for `accumulatedImpairmentLoss` (an optional `accumulatedImpairmentAccountId` parameter, added after the pre-existing required parameters so no positional call site broke) - if the asset has been impaired but no such account is supplied, `dispose()` returns `null` rather than silently computing a wrong gain/loss. **Deliberately does not recalculate `annualDepreciationCharge` over the remaining useful life after an impairment** (IAS 36.63's fuller rule) - straight-line depreciation keeps running on the original schedule regardless, the one confirmed simplification.
- **Work-in-Progress inventory stage — built and tested 2026-08-14, closing the harder half of this gap.** `com.theprodeogroup.fish.domain.inventory.InventoryStage` (`RAW_MATERIAL`/`WORK_IN_PROGRESS`/`FINISHED_GOODS`), 10 passing tests, 304 total in the repo. `StockItem` gained a `stage: InventoryStage` field, defaulting to `FINISHED_GOODS` (matching every `StockItem` built before this existed - a pure-trading company never needs a different stage, same "forgiving default" precedent as `CashBookEntry.cashFlowActivity`). Three new cost-flow methods, all returning `ValidationResult` like `recordReceipt`/`recordIssue` - **none post a `JournalEntry`**, matching the existing precedent that `StockItem` never posts anything itself:
  - `consumeInto(workInProgress, quantity)` - Direct Materials, the first leg of IAS 2's cost build-up. Requires `this.stage == RAW_MATERIAL`, target `== WORK_IN_PROGRESS`.
  - `addProductionCost(cost)` - labour/factory overhead added directly to a Work in Progress item's accumulated cost, no source `StockItem` (it's an incurred cost, not a transfer). `quantityOnHand` unchanged, `unitCost` rises - exactly IAS 2's "cost accumulated to date."
  - `completeInto(finishedGoods, quantity)` - the Cost of Production transfer out of the Manufacturing Account. Requires `this.stage == WORK_IN_PROGRESS`, target `== FINISHED_GOODS`.
  - `consumeInto`/`completeInto` share a private `transferTo()` helper (identical shape: reduce source via `recordIssue`, blend into destination via `recordReceipt`) that **validates stages and currency match before mutating anything** - a real correctness point, not just style: without that ordering, a currency mismatch on the destination side could leave the source already short a quantity that never arrived anywhere.
  - **Deliberately no `ProductionOrder`/job-costing aggregate** - a caller must call these three methods directly in the right sequence; no orchestration, no completion-percentage tracking, no batch/job identity. Confirmed as the scoped-down version before building (a bare stage tag was the alternative considered and rejected, since it wouldn't satisfy IAS 2's actual WIP definition - cost genuinely accumulating, not just a label).
- **Overhead allocation by normal capacity — built and tested 2026-08-14, closing IAS 2.13's "genuine new formula" gap.** `com.theprodeogroup.fish.domain.inventory.OverheadAllocation`, 8 passing tests, 312 total in the repo. A pure calculation, no aggregate identity - same "query/report layer" shape as `TrialBalance`/`WorkingCapital`, applied to a costing figure instead of a balance-sheet one. `OverheadAllocation.calculate(normalCapacity, actualProduction, fixedOverheadPool, variableOverheadPool)`:
  - **Fixed overhead** is allocated at a rate based on `normalCapacity`, not `actualProduction` - IAS 2.13's core rule ("not increased as a consequence of low production or idle plant"). Computed as `fixedOverheadPool * actualProduction / max(normalCapacity, actualProduction)` - a single formula (no branching) that also satisfies the standard's other direction: "in periods of abnormally high production, the amount allocated to each unit is decreased," since dividing by `actualProduction` when it exceeds `normalCapacity` caps `allocatedFixedOverhead` at exactly `fixedOverheadPool`, never more. `unallocatedFixedOverhead` (the difference) is meant to be expensed in the period incurred, never capitalised - this type doesn't post that expense itself, matching the "no `JournalEntry` here" precedent below.
  - **Variable overhead** has no normal-capacity concept at all per IAS 2.13 - `allocatedVariableOverhead` is always the full `variableOverheadPool`, allocated by actual use.
  - `totalAllocatedOverhead` (`allocatedFixedOverhead + allocatedVariableOverhead`) is the figure a caller feeds into `StockItem.addProductionCost()` - composes for free with the WIP cost-flow methods above, no new integration code needed. **Deliberately no `JournalEntry` posting** - matches `StockItem`'s own precedent that it never posts anything itself; posting `unallocatedFixedOverhead` as a period expense is left to the caller.
- **The Manufacturing → Trading → P&L cascade — built and tested 2026-08-14, closing this section's last confirmed step.** `com.theprodeogroup.fish.domain.ledger.ManufacturingTradingProfitAndLossAccount`, 6 passing tests, 318 total in the repo. Same "query/report layer, no new domain invariants" shape as `TrialBalance`/`ProfitAndLoss`/`WorkingCapital` - a richer grouping of the same Expense accounts `ProfitAndLoss` already sums flat.
  - **A real gap found and closed before building the report itself:** `ExpenseClassification` had no value for a pure trader's plain Cost of Goods Sold (goods bought and resold as-is, never touching a Manufacturing Account). Added `COST_OF_GOODS_SOLD` as a 7th value, confirmed by the user over the alternative (treating every unclassified Expense account as Cost of Sales, which breaks for a services company with no COGS concept at all).
  - **Manufacturing Account:** `primeCost` = `DIRECT_MATERIAL` + `DIRECT_LABOR` + `DIRECT_EXPENSE`; `totalManufacturingCost` = `primeCost` + `FACTORY_OVERHEAD`; `costOfProduction` = `totalManufacturingCost` + `openingWorkInProgress` − `closingWorkInProgress`, where opening/closing WIP is derived from a caller-supplied `workInProgressAccount`'s posted balance before/through the `Period`, the same opening/closing mechanism `StatementOfCashFlows` already uses for cash.
  - **Trading Account:** `costOfSales` = `costOfProduction` + `COST_OF_GOODS_SOLD` - the *sum* of both paths into Cost of Sales (a manufacturer's built-up Cost of Production, and a pure trader's direct COGS); a company using only one path simply has zero in the other. `grossProfit` = `revenue` − `costOfSales`.
  - **P&L Account:** `operatingExpenses` = `totalExpense` − (`totalManufacturingCost` + `COST_OF_GOODS_SOLD`) - computed as a remainder rather than enumerating `ADMINISTRATIVE`/`SELLING_DISTRIBUTION`, so an Expense account nobody got around to classifying still counts toward `netProfit` instead of silently vanishing.
  - **Verified algebraically, not just by test, that the cascade never changes the bottom line versus the simpler `ProfitAndLoss`:** `netProfit` always reduces to `revenue − totalExpense − openingWorkInProgress + closingWorkInProgress` regardless of how the Manufacturing/Trading stages group the same Expense accounts - the three-stage view only exposes the intermediate Gross Profit/Cost of Production figures, it doesn't create or destroy value. A dedicated test increases WIP during the period and confirms Cost of Production (and thus Net Profit) reflects the deferral correctly.
- **Still open: abnormal-waste expensing** - as flagged above, the last item from this grounding. NRV write-down, IAS 23 capitalisation, and IAS 36 impairment are all built (Section 2.6/2.1 above), no longer open.

### 2.8 Fixed Asset Register (core built 2026-08-12)

Named by the user 2026-08-11: "we will need a fixed asset register," resolving the open question in Section 3.1's `Account`/depreciation note (fields on `Account` vs. a dedicated register — settled in favor of the register). Follows the same control-account + subsidiary-ledger pattern already established for AP/AR (Section 2.5): a Fixed Assets control account lives in core Ledger; per-asset detail lives in this module, with the same tally requirement between them (not enforced by the domain model itself, same as AP/AR — a future reconciliation/reporting concern).

**Scope confirmed 2026-08-12** (park-don't-guess, matching every prior increment this session): **straight-line depreciation only** — no pluggable method yet, reducing-balance and others can be added later without breaking this shape — and **acquisition + periodic depreciation only** — disposal/write-off deferred to a later increment, matching how Inventory/Payroll stayed minimal on their first pass.

`com.theprodeogroup.fish.domain.fixedassets` — **`FixedAsset`** (`id`, `companyId`, `name`, `category: AssetCategory` [`LAND`/`BUILDINGS`/`EQUIPMENT`/`VEHICLES`, the same four categories this section's own earlier draft named], `cost: Money`, `acquisitionDate`, `usefulLifeYears: Int?`), self-tracked `accumulatedDepreciation: Money` (private-set), computed `netBookValue = cost - accumulatedDepreciation` and `annualDepreciationCharge = cost / usefulLifeYears` (straight-line, `null` if `usefulLifeYears` is `null`). 8 passing tests, 190 total in the repo.

- **Land is enforced as non-depreciable at construction** (`require(category != LAND || usefulLifeYears == null)`) — the confirmed policy from Section 3.1's depreciation note, not left to accidental omission.
- **`recordDepreciation(depreciationExpenseAccountId, accumulatedDepreciationAccountId, periodId, date)`** debits the expense account, credits `accumulatedDepreciationAccountId` for one year's straight-line charge, using `JournalSource.SYSTEM` (that enum's own original "monthly depreciation entry" example, now actually used). **Accumulated depreciation uses one shared contra-asset control account, not one per category** — the simplest default given the open sub-question this section originally flagged, not a confirmed policy either way. The charge is **capped at remaining `netBookValue`**, so a straight-line division that doesn't divide evenly (e.g. £1000 over 3 years = £333.33 × 3 = £999.99, a £0.01 rounding remainder) gets captured in full by whichever call crosses it, rather than silently over- or under-depreciating. Returns `JournalEntry?` — `null` if the asset has no `usefulLifeYears` (e.g. Land) or is already fully depreciated, matching `PurchaseOrder.send()`/`SalesOrder.deliverLine()`'s precedent.
- **One `recordDepreciation()` call represents one full year's charge**, not a period-fraction proration — matches the existing boundary discipline of `JournalEntry` never inspecting `Period`'s own type/duration (Section 3.1's design note); callers decide their own posting cadence.

**Disposal — built and tested 2026-08-12, closing the deferral above. Corrected same day to the standard Asset Disposal Account method**, per the user's own detailed description of UK bookkeeping practice — the first version computed gain/loss directly with its own if/else branching and a separate gain/loss account; the corrected version lets the ledger derive it, matching how the technique is actually taught. `dispose(proceeds, cashAccountId, fixedAssetAccountId, accumulatedDepreciationAccountId, saleOfFixedAssetAccountId, periodId, date)`: `saleOfFixedAssetAccountId` ("Sale of Fixed Asset," a Revenue-type account) is the **clearing account everything routes through**, not a separate gain-only target — (1) debit Sale/credit Fixed Asset for `cost`, (2) debit Accumulated Depreciation/credit Sale for `accumulatedDepreciation` (after steps 1-2 alone, Sale's net balance is exactly `netBookValue`, confirmed by the user's own stated constraint), (3) debit Cash/credit Sale for `proceeds`. **No gain/loss computation or dedicated account exists in the code at all** — whatever balance remains on `saleOfFixedAssetAccountId` after all three postings *is* the gain (a credit balance, matching its Revenue type) or loss (an abnormal debit balance). The accumulated-depreciation and proceeds legs are each omitted when exactly zero, same "nothing to post" precedent as `Customer.assessExpectedCreditLoss()`. A new `isDisposed` flag (private-set) blocks both `recordDepreciation()` and a second `dispose()` call afterward. 5 tests (rewritten to verify the account nets to the expected gain/loss balance rather than asserting a dedicated gain/loss line), 247 total in the repo.

**Deliberately still deferred:** reducing-balance/other depreciation methods, per-category contra-asset control accounts (single shared account is the current default, not a confirmed final answer), land revaluation (IAS 16's confirmed OCI/equity-reserve treatment from Section 3.1 still applies whenever this gets built). Whether Fixed Asset Register is its own bounded context or shares one with Inventory Management (both manage physical/capital items) remains open, unaffected by this increment.

### 2.9 Party — Counterparty Identity (design proposal, 2026-08-12, not yet built)

Proposed by the user 2026-08-12, not yet implemented — this section documents the design so retrofitting is deliberate when it happens, not guessed at. No code changes accompany this section.

**The insight:** `Creditor` (Section 2.5), `Customer` (Section 2.5), and Payroll's `EmployeeId` (Section 2.7, already reference-only with no aggregate behind it) all model the same underlying kind of thing — a counterparty with a name, an identity, potentially an address/tax registration — playing a different **role** depending on which context is looking at it. The same real-world legal or natural person can be a Supplier in one Purchase Order and a Customer in one Sales Order; nothing in the current design lets that be represented as one identity. **IFRS backs this reading**: no IFRS/IAS standard defines "customer" or "supplier" as a fixed ontological category — they attach standards to *contracts and obligations* instead (IFRS 15 to a customer contract, IFRS 9 to a financial liability/asset, IAS 19 to employee benefits, IAS 24 to related-party relationships), and the same counterparty can be the subject of more than one.

**Pattern chosen: Party-Role composition, not GoF Decorator.** The user's original framing suggested the Decorator pattern (wrapping a core `Person`/`Party` object to imbue it with role behaviour at runtime). Recommended alternative, for two concrete reasons:
1. GoF Decorator wraps an object behind a shared interface at runtime — that fights the aggregate/repository convention already established throughout this codebase (`Creditor.create()`, `Customer.create()`, private constructor + companion factory, each aggregate owning its own persistence boundary). There's no clean way to persist "a Party wrapped in a CustomerDecorator wrapped in a StaffDecorator" through a repository without inventing new machinery this codebase doesn't otherwise need.
2. If role behaviour (postings, balances, invariants) gets attached directly to a shared `Party` object — decorator or not — `Party` risks becoming one large, contended aggregate that every context needs to load and mutate. That's exactly the shape of aggregate the codebase has so far deliberately avoided (`Creditor` and `Customer` are already separate, independent aggregates specifically so AP and AR/Income's asymmetric recognition timing, Section 2.5, don't share a consistency boundary).

Instead: **`Party` is its own lightweight aggregate holding identity only.** Each role — `Creditor` (Supplier role), `Customer` (Customer role), and future `Staff`, `Borrower`, `Lender`, `Shareholder`, `Director`, `RelatedEntity` roles — stays its **own** aggregate, exactly as already built, and gains a `partyId: PartyId` reference back to the shared identity. Nothing about `Creditor`'s or `Customer`'s existing balance-tracking, control-account posting, or `ValidationResult` behaviour changes — Party sits *behind* them as a shared identity lookup, not *around* them as a wrapper.

**What lives where — the key clarifying split, since the user's own list of shared attributes (addresses, identifiers, tax registrations, credit limits, transaction histories) mixes two different kinds of thing:**
- **On `Party` (identity, stable across roles):** name, party type (individual vs. organization — covers both natural and legal persons, "Party" rather than "Person" specifically to avoid the natural-person-only reading), and eventually a tax identifier and address. **Not decided in this pass:** the exact shape of address/tax-identifier fields — no `Address` value object exists anywhere in the codebase yet, and inventing one casually here would be guessing ahead of a real need, the same discipline already applied to Inventory (Section 2.6) and Payroll (Section 2.7).
- **On the Role aggregate (relationship-specific, varies per role):** credit limit, running balance, payment terms, and transaction history. The user's list named "credit limits" as something Customer and Supplier share — true, but that's because both roles *extend credit*, not because `Party` itself has a credit limit; a `Staff` or `Borrower` role wouldn't share that field the same way. These terms stay exactly where they already live (`Creditor.balance`, `Customer.balance`), not on `Party`.
- **Roles are derived, not stored on `Party`.** `Party` does **not** keep a `roles: Set<PartyRoleType>` field — "what roles does this Party currently play" is discoverable by querying which role aggregates (`Creditor`, `Customer`, future `Staff`, ...) reference a given `partyId`, not by a redundant field on `Party` that could drift out of sync with the actual `Creditor`/`Customer` records.
- **Transaction history is a read-model/reporting concern**, not something `Party` stores directly — consistent with how the Trial Balance and P&L/Income-and-Expenditure reports are already flagged elsewhere in this doc as future reporting work, not aggregate state. It would be derived by querying across whichever role aggregates reference a given `partyId`.

**IFRS mapping per role, extending the "two standards" pattern already used for AR/AP (Section 2.1/2.5) and Inventory (Section 2.6):**
- **Customer role → IFRS 15** (revenue/contract asset) — already governs Sales Order Processing's income recognition (Section 2.5); no change, just now framed as attaching to the Customer *role* of a Party rather than to a standalone `Customer` concept.
- **Supplier/Creditor role → IFRS 9** (financial liability) — already governs Purchase Order Processing's AP recognition (Section 2.5); same reframing, no behavioural change.
- **Staff role → IAS 19** (Employee Benefits) — a standard not referenced anywhere else in this doc until now. **Gap surfaced by this design exercise, parked, not built:** Payroll's current build (Section 2.7) posts gross pay/deductions/net pay/employer costs per `Payslip`, but doesn't model an ongoing *employee benefit obligation* (e.g. accrued-but-unpaid wages, holiday-pay accrual) the way IAS 19 would eventually require. **A `Staff` role aggregate, if built, would relate to `Payslip` exactly the way `Creditor` relates to `PurchaseOrder`**: `Payslip.post()` would call `staff.accrue(netPay)`/`staff.settle(...)` alongside emitting its `JournalEntry`, giving Payroll the subsidiary-ledger balance it currently lacks — the same control-account/subsidiary-ledger mechanism as AP/AR, not a new one. Still parked, not built.
- **Related Entity role (Intercompany) → IAS 24** (Related Party Disclosures) — connects to Company parent/consolidation relationships, already confirmed conceptually but parked (see `project_company_relationships_rag` in memory), not yet built at field/aggregate level.
- **Borrower role → IFRS 9 financial asset** (loan receivable) — a counterparty *Purse lends to* (e.g. a member taking a loan). Lending context (Section 2.3), blocked on the still-unresolved "separate service vs. separate package" deployment question (see `project_lending_separation` in memory).
- **Lender role → IFRS 9 financial liability** (loan payable / deposits) — the mirror image of Borrower: a counterparty *who lends to Purse* (e.g. member deposits/shares, or a wholesale funding line). Same Lending-context caveat as Borrower.

**Naming resolution, confirmed 2026-08-12 — a real collision, not a style choice, caught before any code was written.** An earlier pass through this design sketched a `Supplier` role (AP/Creditor's job, restated under a new name) and a `Creditor` role for the Lending-side liability above. **That collides directly with the `Creditor` that's already built and shipped** (`domain.purchasing.Creditor`, 13 tests) — which already *is* the Supplier/AP role. Resolved in the user's own favour, lowest-risk option: **`Creditor` keeps its existing meaning (AP/Supplier) untouched — no rename, no retrofit to already-tested code.** There is no separate `Supplier` aggregate; `Creditor` already fills that role. The Lending-side liability concept is named **`Lender`** instead of `Creditor` — not a new invented word, it's the same term the user's own original framing already used ("In Lending → they are a Borrower or Lender").

**`Company` vs. `Party` — a boundary worth stating explicitly so it isn't guessed at later.** `Company` (Tenancy context, Section 2.2/3.2) is a FiSH tenant's *own* book-owning entity — it carries tenant-scoped concerns (`GoingConcernStatus`, `ClientType`, Chart of Accounts ownership) that a business's own supplier, customer, or staff member should never have. Even though a `Company` is, in the ordinary sense, also a legal person, it is not the same kind of thing as a `Party` in this model — a `Company` is *who owns the books*, a `Party` is *who the books are about*. **Genuinely open, not decided:** for intercompany transactions specifically (Purse's four Companies transacting with each other), should a `Company` optionally hold its own `partyId` so it can appear as a Related Entity counterparty in *another* Company's AR/AP? Flagged for later, don't guess at an answer now.

**Retrofit points — exactly where this touches existing code, if/when it gets built (nothing below has been changed yet):**
1. New package `com.theprodeogroup.fish.domain.party` — `PartyId` (`@JvmInline value class`, same convention as every other ID in the codebase) and a `Party` aggregate (`id`, `name`, `partyType`; address/tax-identifier fields deferred as above).
2. `GL/src/main/kotlin/com/theprodeogroup/fish/domain/purchasing/creditor.kt` — `Creditor` would gain a `partyId: PartyId` field; `Creditor.create()`'s signature changes, a breaking change to already-tested code (`CreditorTest.kt`, 6 cases, would need updating).
3. `GL/src/main/kotlin/com/theprodeogroup/fish/domain/sales/customer.kt` — same retrofit as `Creditor`; `CustomerTest.kt` (6 cases) affected identically.
4. `GL/src/main/kotlin/com/theprodeogroup/fish/domain/payroll/ids.kt` and `payslip.kt` — **genuinely open, not decided:** does `EmployeeId` (already deliberately reference-only, Section 2.7) get retired in favour of `Payslip` referencing `PartyId` directly, or does it stay as its own role-identifier that itself references a `PartyId`? Both are viable; flagging rather than picking.
5. Whether `name`/`currency` stay duplicated on `Creditor`/`Customer` as denormalized display fields (common practice in real accounting systems — avoids forcing every read through a `Party` join, and avoids a larger breaking change) or get removed in favour of always reading through `Party` — a design call to make at build time, not decided here.
6. New role aggregates for **`Staff`** (Payroll/IAS 19), **`Borrower`** and **`Lender`** (Lending/IFRS 9) — none exist yet, blocked on the same "no forcing use case yet"/Lending-deployment-topology open questions as above. If/when built, `Staff.staffId` would replace `Payslip.employeeId: EmployeeId` per point 4.
7. **Nothing changes in `Account`, `JournalEntry`, or the control-account mechanism (Section 2.5)** — `Party` sits entirely behind the existing `Creditor`/`Customer`/`Payslip` aggregates as a shared identity lookup; it doesn't touch Ledger's own consistency boundary.

**Convention corrections for any future implementation, so a code sketch's illustrative shorthand doesn't get mistaken for what this codebase already does:**
- ID types (`PartyId`, `StaffId`, `BorrowerId`, `LenderId`, etc.) should be `@JvmInline value class Xxx(val value: UUID)` with a `companion object { fun generate() = Xxx(UUID.randomUUID()) }`, matching every existing ID in the codebase — not a bare `data class`.
- Balance-mutating methods (`postInvoice`/`postBill`/`accrue`/`disburse`/etc.) should validate (positive amount, matching currency) and return `ValidationResult`, matching `Creditor.recordCharge()`/`recordPayment()`'s established Notification-pattern precedent — not mutate `balance` directly with no validation.
- `Money` has no `zero(currency)` factory today — only a `BigDecimal` + `Currency` constructor (`Money(BigDecimal.ZERO, currency)`).

**Why this stays a design-only section for now:** no increment built so far actually needs one counterparty resolving to two roles — nothing in the test suite has hit "this Supplier is also a Customer." Building `Party` now would be building ahead of a forcing use case, which the project has deliberately avoided at every prior increment (Section 2.6/2.7's "start disconnected"/"core posting only" scoping). Revisit when Lending, Intercompany, or a real duplicate-counterparty case actually needs it.

### Context relationships
- Scrip (Rust) and Osusu (Kotlin) are **external** to all four contexts — they're API clients of Ledger (and, per the spec's 7.13/7.14, Scrip is where `EquityStake` and business-health classification logic actually live, even though the *data* originates in FiSH).
- Lending and Tax both depend on Ledger; Ledger depends on neither. This dependency direction is the one invariant to protect as the codebase grows — if Ledger ever needs to import from Lending, that's a signal the boundary has been drawn wrong.

### 3.1 Ledger context

**Account** (aggregate root — **built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.ledger.Account`, 14 passing tests)
- Identity: `AccountId`.
- Invariants: belongs to exactly one Company; type is one of Asset/Liability/Equity/Revenue/Expense (`AccountType`, with `normalBalance(): TransactionSide` and `requiresClassification(): Boolean` helpers); cannot be hard-deleted once it has posted activity — `validateDeletion()` rejects with `ValidationResult.failure` if `recordActivity()` has been called, deactivation (`deactivate()`/`reactivate()`) is offered instead.
- **IAS 1 current/non-current classification, built as specified:** Asset/Liability accounts require an `AccountClassification` (`CURRENT`/`NON_CURRENT`); Equity/Revenue/Expense accounts must *not* have one — both directions enforced at construction (`Account.create()` throws `IllegalArgumentException` via `require()`, matching `Money`'s precedent for constructor-time invariants, rather than `ValidationResult` which is used for post-construction transitions here, matching `Tenant`'s precedent). Covenant-triggered reclassification still deliberately not built (Section 3.1's original note stands).
- **`ExpenseClassification` — manufacturing accounting, first step built 2026-08-12.** `Account` gained a second, optional sub-classification (`DIRECT_MATERIAL`/`DIRECT_LABOR`/`DIRECT_EXPENSE`/`FACTORY_OVERHEAD`/`ADMINISTRATIVE`/`SELLING_DISTRIBUTION`), the smallest first step toward a three-stage **Manufacturing Account → Trading Account → Profit & Loss Account** structure (confirmed the correct shape for manufacturing companies, not the two-stage Trading/P&L split first floated when `PayRun` was built — production wages sit *inside* the Manufacturing Account as Direct Labor, not directly in Trading). `AccountType.requiresExpenseClassification()` mirrors `requiresClassification()`'s shape but **not its enforcement**: current/non-current is a near-universal IAS 1 requirement for every Asset/Liability account, while `ExpenseClassification` only matters to a company that wants a Manufacturing Account at all — `Account.create()` only enforces the reverse direction (a non-Expense type can't be given one), it doesn't require every Expense account to have one. 4 new tests, 294 total in the repo. **Deliberately just the classification** — `ProfitAndLoss` doesn't yet compute a cascading three-stage result from it, and Work-in-Progress (the harder, more novel piece — an inventory stage between Raw Materials and Finished Goods, with its own opening/closing balance) isn't modeled at all; `StockItem` (Section 2.6) is still a single flat stage. Both are the confirmed next steps, not attempted here.
- **Parent hierarchy, partially built:** only a self-parent cycle is checked at construction (`parentId != id`) — deeper multi-level cycle detection and cross-Company parent validation need the full Account tree, which a single aggregate can't see in isolation. Flagged in code as an application-service-level concern, the same way `PostingService` checks `Period.status` outside `JournalEntry` itself (design note below) — **not built yet**, since there's no repository/application layer at all in this codebase so far.
- Depends on: `Company` (by reference/ID only, not embedded) — `com.theprodeogroup.fish.domain.tenancy.CompanyId`, a real cross-context reference now that both packages exist.
- **Fixed vs. Current Assets, confirmed 2026-08-11 — already covered by `AccountClassification`, no new field needed.** The user's own framing: "Assets also are Fixed or Current." This is the same `CURRENT`/`NON_CURRENT` split already built for IAS 1 (above) — "Fixed Asset" is just the common name for a `NON_CURRENT` Asset account, not a separate classification to add.
- **Depreciation, resolved 2026-08-11 — a Fixed Asset Register, not new fields on `Account`. Core built 2026-08-12, see Section 2.8.** Fixed Assets are "likely to incur depreciation charges over time depending on how long is required by the system user" — i.e., useful life is a user-configurable input, not a hardcoded rule. The user confirmed: "we will need a fixed asset register," settling the shape question left open earlier. Follows the same control-account + subsidiary-ledger pattern as AP/AR (Section 2.5/2.8): a Fixed Assets control account lives in core Ledger, per-asset detail lives in the **Fixed Asset Register** module (`FixedAsset`, Section 2.8), with the same tally requirement between them. Periodic depreciation postings use `JournalSource.SYSTEM` — already anticipated in that enum's own original KDoc example ("Monthly depreciation entry"), written before this session even started, now actually used by `FixedAsset.recordDepreciation()`. Confirmed scope: straight-line only, a single shared contra-asset control account (not one per category — genuinely still open, not a final answer), disposal deferred.
- **Land: confirmed policy 2026-08-11, not just a default assumption anymore.** Land is not depreciated (indefinite useful life, unlike buildings/equipment). If/when land revaluation is built, the user confirmed the IAS 16 treatment should be followed: revaluation gains route through **Other Comprehensive Income into a separate revaluation reserve within Equity**, not straight through P&L. Both points are now confirmed policy to build toward when this gets designed in detail — not tentative, though still not built.

**JournalEntry** (aggregate root — **built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.ledger.JournalEntry`, 12 passing tests; `JournalLine` is part of the same aggregate — not its own root)
- Identity: `JournalEntryId`.
- Invariants: sum of debit `Money` amounts equals sum of credit `Money` amounts, *per currency* (a multi-currency entry needs care here — see open question below); `PostingStatus` transitions only via `canTransitionTo()`; once `Posted`/`System`, immutable except for a `Reversed` transition; every entry carries a `JournalSource`.
- **Balance validation matches Section 6's literal spec — `ValidationResult`, not throw, at the check itself.** `JournalEntry.validateLines()` is a standalone companion function returning `ValidationResult`, callable before construction; `create()` calls it internally and `require()`s success (throws `IllegalArgumentException` for a caller that skipped the pre-flight check) — matching `Account`/`Money`'s precedent for construction-time invariants, while still honoring the spec's literal wording for the validation step itself.
- **`post()`** — Draft/Pending → Posted, raises `JournalEntryPosted` (Section 4, now actually built) via the same `pullDomainEvents()` pattern as `Tenant`.
- **`reverse()`** — Section 6: creates and returns the reversal entry (new `JournalEntryId`, `JournalSource.REVERSAL`, lines with `TransactionSide.opposite()` — a small addition to that enum, needed to construct lines that exactly cancel the original), transitions the original to `Reversed`. Returns `null` (not a `ValidationResult`) if the entry isn't in a reversible state, since this method's job is producing a new object on success, not just mutating `this`. The reversal entry starts already `Posted`, not `Draft` — it's system-generated and needs to take effect immediately; its balance is guaranteed by construction (swapping every line's side preserves the balance identically), so it bypasses `create()`'s validation.
- Contains: one or more `JournalLine` value objects/entities, each referencing an `AccountId` and carrying a `Money` amount + `TransactionSide` + optional `DimensionType` tags (`Map<DimensionType, String>`, defaults empty).
- Depends on: `Account` (by ID), `Period` (by ID, to check postability — see below). **`Period.status` is deliberately never checked by `JournalEntry` itself** — no test for this exists in `JournalEntryTest.kt` on purpose, matching the design note below; that check belongs to `PostingService`, still not built.
- **The accounting equation, confirmed 2026-08-11 — a system-level invariant, not a new rule to enforce separately.** The user's own framing: "the total sum of all Asset balances must equal the total sum of all Liability and Capital balances." This is `Assets = Liabilities + Equity` — and it's a **derived, emergent property** of every `JournalEntry` being balanced (debits = credits), not an independent check that needs its own enforcement mechanism. If every posted entry balances, the whole ledger balances automatically: summing every account by its `normalBalance()` (`AccountType.normalBalance()`, already built), `Σ(Asset + Expense balances) = Σ(Liability + Equity + Revenue balances)` holds identically — this is the more general, always-true form (including Revenue/Expense, which is what actually holds continuously, before any period-end closing entries move net income into Equity). **Trial Balance — built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.ledger.TrialBalance`, 6 passing tests. `TrialBalance.of(accounts, postedEntries, currency)` computes each Account's balance (via a new shared `accountBalances()` helper) in its own `normalBalance()` direction, summed into `totalAssetAndExpense`/`totalLiabilityEquityRevenue`, with `isBalanced` checking they're equal — exactly the check/report this note originally flagged, now real. A snapshot of all posted activity so far, not scoped to a single `Period` (unlike `ProfitAndLoss` below) — Balance Sheet-style accounts are point-in-time, not period-bound. Assumes a single [currency]; multi-currency consolidation (Section 8's open question) is still unsolved — mixing currencies throws via `Money.plus()`'s existing guard rather than silently producing a wrong number.

**A real, previously-unexercised edge case surfaced while building this:** `PostingStatus.affectsBalance()` (pre-existing, `domain.common`) excludes `REVERSED` — reusing it here would have made a reversed entry's original postings vanish from the Trial Balance while its paired reversal entry (itself `Posted`) still counted, doubling the error instead of netting to zero. `accountBalances()` uses a new, reporting-specific `hasHistoricalEffect()` predicate instead (`POSTED`/`SYSTEM`/`REVERSED` all count — `REVERSED` genuinely happened, its effect is only cancelled by summing it *together with* its reversal; only `DRAFT`/`PENDING`/`REJECTED` never had real effect). Caught by a test (`given a posted entry and its posted reversal... net effect is zero`) before it could ship as a silent correctness bug in the first feature to actually sum multiple `JournalEntry`s together — nothing built before this needed to.

**Second report confirmed 2026-08-11, built 2026-08-12 alongside Trial Balance:** the user wants Revenue and Expense shown **separately** too — a **Profit & Loss / Income and Expenditure Account** (the latter is the correct term for Purse specifically, given its `ClientType.NON_PROFIT` classification, Section 8 — matches the GL's own stated purpose of letting a Company "recognise its own income, expenditure, capital, assets and liabilities," Section 2.1). `com.theprodeogroup.fish.domain.ledger.ProfitAndLoss`, 5 passing tests, 166 total in the repo. `ProfitAndLoss.of(accounts, postedEntries, periodId, currency)` filters entries to the given `PeriodId` first, then reuses the same `accountBalances()` helper as `TrialBalance` to compute `totalRevenue`/`totalExpense`; `netIncome = totalRevenue - totalExpense` (a computed property, can go negative — a loss). "Income and Expenditure Account" is a report-title concern, not a different class — the underlying computation is identical for any `ClientType`. The distinction from Trial Balance/Balance Sheet: **Balance Sheet accounts (Asset/Liability/Equity) are point-in-time** (as-at a date), while **Income Statement accounts (Revenue/Expense) are period-bound** (for the month/year ended) — `ProfitAndLoss` is always scoped to one `Period`, unlike `TrialBalance`.

**Period** (aggregate root — **built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.ledger.Period`, 8 passing tests)
- Identity: `PeriodId`.
- Invariants: `PeriodStatus` transitions only via valid paths (Draft→Open→Closed→Locked, Closed→Open reopen); posting is only allowed when `allowsPosting()` is true. Core fields: `companyId`, `periodType` (`PeriodType`), `startDate`/`endDate` (`LocalDate`, `endDate` cannot precede `startDate` — thrown at construction, matching `Account`/`Money`'s precedent).
- **`PeriodStatus.isValidTransition(from)` renamed to `canTransitionTo(newStatus)` while building this** — the Section 0 gap 6 inconsistency ("worth aligning both to the same calling convention when this file is next touched") is now fixed, since `Period` is the first real consumer of `PeriodStatus`. Semantics preserved exactly, just flipped calling direction to match `PostingStatus.canTransitionTo()`; zero blast radius since nothing called the old method yet.
- **Design note:** `JournalEntry` posting must check `Period.status`, but `Period` should *not* be inside `JournalEntry`'s consistency boundary (they change at different rates and for different reasons). Enforce "no posting into a closed period" as an **application-layer/domain-service check** (`PostingService`, not yet built) that loads both and validates, rather than merging them into one aggregate. This is a standard DDD trade-off worth being deliberate about rather than accidental. `Period.allowsPosting()` is the primitive that service will call.

**Money** (value object — **built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.ledger.Money`)
- `amount: BigDecimal`, `currency: Currency` (ISO 4217 code). `plus()` and `compareTo()` (via `Comparable<Money>`) throw `IllegalArgumentException` on mixed currencies rather than silently producing a wrong number — resolved as "throw," not `ValidationResult`, since Kotlin operator overloads and `Comparable.compareTo` need to return their natural type (`Money`/`Int`), not a wrapped result.
- **Design addition beyond the original spec, needed for correctness:** the constructor normalizes `amount` to the currency's minor unit (`currency.defaultFractionDigits` — 2 for GBP/USD, 0 for JPY) using `RoundingMode.HALF_EVEN`, and `equals()`/`hashCode()` are overridden to compare by numeric value rather than raw `BigDecimal.equals()` (which is scale-sensitive — `10.0` and `10.00` are unequal under the JDK default). Without this, two `Money` values representing the same amount could compare unequal depending on how they were constructed — a real bug class for a financial type, not a hypothetical one.
- 11 passing tests, `MoneyTest.kt` — same-currency addition, cross-currency addition/comparison rejected, scale-insensitive equality, minor-unit rounding. **Verified directly against the actual Mano River launch markets (spec §2.6/7.12), not just JPY as a generic example:** checked `java.util.Currency` at the JDK level and confirmed Guinea (GNF) and Côte d'Ivoire (XOF) are genuinely zero-decimal currencies, same shape as JPY — while Sierra Leone (SLL/SLE) and Liberia (LRD) are 2-decimal. Two of the four launch markets would have been silently mishandled by a naive "always round to 2 decimal places" implementation; the `currency.defaultFractionDigits`-driven design handles all four correctly without special-casing. Explicit test cases added for GNF/XOF/SLE/LRD, not just the generic JPY case.
- This blocked `JournalLine` from being written correctly per the original design note — now unblocked. `Account` is next per the Section 6 build order.

**CashBookEntry** (**built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.ledger.CashBookEntry`, 7 passing tests — a book of original entry, not a separate ledger)
- Resolved: FiSH's Cash/Bank Book is a **simplified single-sided capture** that generates a proper `JournalEntry` behind the scenes, not a new parallel ledger and not just a read-only view over existing `JournalEntry` lines. Consistent with the non-accountant UX principle already established (memory: `feedback_non_accountant_ux`) — the person recording "money came in" or "money went out" shouldn't need to know which side is debit and which is credit.
- Fields, built as designed: `accountId` (the Cash/Bank `Account`), `direction` (`CashDirection.RECEIVED`/`PAID` — a new small enum, plain language, not `TransactionSide` directly), `amount: Money` (must be positive — `require()`s at construction; a negative "amount received" is a user error, use `direction` instead), `counterAccountId`, `date`, `description` (optional).
- **`toJournalEntry(periodId, id)`** derives the balanced `JournalEntry` — the Cash/Bank `Account` takes the `TransactionSide` implied by `direction` (received → `DEBIT`, paid → `CREDIT`, using `TransactionSide.opposite()` for the counter-account's line), assuming `accountId` is always an Asset-type account (Cash/Bank), not a generic conversion for any Account type. This is the concrete mechanism implementing the "correct side" logic non-accountant users shouldn't have to think about.
- **Not a persisted aggregate** — a lightweight command/DTO with no `id`/repository of its own, matching the "current lean" already recorded when this was first designed. The `JournalEntry` it produces is what gets persisted.
- **`JournalSource.MANUAL`** used rather than a new enum value — reasoned default: a real person initiated the entry even though the UI simplifies the mechanics, which is the distinction `JournalSource`'s existing values actually track (human vs. system/API/integration-initiated), not worth a new value for this alone. Flagged as a judgment call, not re-litigated from the earlier "still open" note.
- Depends on `Account` and `JournalEntry`, both now built — this is a consumer of the Ledger core, not a replacement for it. **This completes the feature that originally motivated starting the Money → Account → Period → JournalEntry build order.**
- **Not yet decided:** exact `JournalSource` value for entries originating this way (existing values — `MANUAL`, `IMPORT`, etc. — don't quite name it; Section 9.8 flagged a similar gap for opening-balance entries specifically, this may be the same value or a different one). Whether `CashBookEntry` is a first-class persisted aggregate in its own right, or just an application-service-level DTO/command that produces a `JournalEntry` and is never stored itself, is also open — leaning toward the latter (simpler, no extra aggregate to keep consistent) but not decided.

### 3.2 Tenancy & Access context

**Tenant** (aggregate root) — owns Companies, Memberships, tenant-level settings (COA template, base currency, fiscal calendar).
**Company** (aggregate root — **built and tested 2026-08-11**, `com.theprodeogroup.fish.domain.tenancy.Company`, 4 passing tests, referenced by ID from Ledger, not embedded in Tenant) — one legal entity, its own COA and books. Core fields only, per the agreed minimal-build scope: `tenantId` (reference), `name`, `clientType` (`ClientType`), `jurisdiction` (plain `String`, matching `Tenant`'s precedent of not over-typing simple fields), `baseCurrency` (`Currency` — a Company's own, not inherited from Tenant, since jurisdictions can differ within one Tenant, e.g. Purse's UK/NI/ROI/SL). Carries a `goingConcernStatus` (`GoingConcernStatus` — resolved 2026-08-11, see Section 9.7, **built as a 2-state enum with `canTransitionTo()`**): every Company defaults to `ASSUMED` going concern at creation — this is the standard accounting default, not a special case — and can move to `SUBSTANTIAL_DOUBT` via `flagSubstantialDoubt()`, which the (not yet built) Lending context will call when a business borrower's `ArrearsCase` reaches `Final Resolution`. **No reversal built** — `SUBSTANTIAL_DOUBT → ASSUMED` deliberately doesn't exist yet, since how that should work is still an open question (Section 9.7).
- **Company relationships, confirmed 2026-08-11 — not yet built.** A Tenant's Companies can relate to each other, not just sit side by side — the user's own framing: "he sets up his company or companies and the relationships between them (e.g. consolidation of accounts or separate accounts)." Concretely: a `parentCompanyId: CompanyId?` (mirroring the parent/child pattern already built on `Account`), plus a consolidation mode — whether a Company's figures combine into group reporting with its parent, or stay standalone. Real implication for the Trial Balance/P&L reports flagged in Section 3.1 (JournalEntry note): they'll eventually need both a per-Company view and a consolidated-group view, not just per-Company. Not designed in detail yet — this is the concept, not the field-level design.
- **Real-time going-concern monitoring (RAG indicators), raised 2026-08-11 — explicitly parked, not decided.** The user's framing: going-concern health measured continuously with Red/Amber/Green indicators, "a bit like real time analysis of blood pressure oxygen etc of a human." This is a meaningfully richer concept than the current `GoingConcernStatus` (a two-value `ASSUMED`/`SUBSTANTIAL_DOUBT` enum, Section 9.7) and it collides with something already decided elsewhere in this doc: Section 2.4's "Context relationships" already states Scrip owns business-health classification logic (spec §7.13/7.14's "business-health signal feed"), consuming data that originates in FiSH rather than FiSH computing it. **Asked directly whether RAG scoring should live in FiSH (expanding `GoingConcernStatus`) or stay in Scrip (FiSH just emits good data/events) — not answered, don't assume either way.** A related, explicitly speculative idea from the same message — "this probably would lead to gamifying the activities of the company" — is flagged as a future product direction only, not scoped or designed.
- **Boundary clarified 2026-08-11, doesn't fully resolve the above but narrows it:** the user distinguished going-concern management (a *diagnostic* question — is the company healthy) from **treasury/investment optimization of company assets, especially current assets** (an *operational* one — actively deploying assets for best use) as "two different things." Treasury/investment is Scrip's stated core identity (CLAUDE.md: "Scrip — Purse's treasury/investment arm"), and its natural data hook is exactly `AccountClassification.CURRENT` — already built on `Account`. This doesn't answer whether RAG scoring lives in FiSH or Scrip, but it does mean: don't design one mechanism trying to serve both going-concern health *and* treasury/investment optimization as if they're the same feature. They may share a data source (FiSH's ledger) without sharing logic or ownership.
**User / Membership — core built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.tenancy.User`/`Membership`, 8 passing tests (3 `User`, 5 `Membership`), 198 total in the repo. Checked the spec first (same discipline as `ArrearsCase`/`WorkingCapital`/`BankReconciliation`) — Section 7.8/10 define more than the design doc previously captured:

- **`User`** — `id`, `email`, `name`. The spec's own User definition is bare ("A person who can log in; may belong to one or more Tenants via Membership") — no fields beyond identity specified. `email`/`name` are the minimal addition needed for a login identifier and display name; authentication mechanics (password, MFA, SSO) are deliberately not modeled, matching every other aggregate keeping infrastructure/security concerns out of the domain layer. Global identity, not scoped to any Tenant. Does **not** track its own `Set<MembershipId>` — which Memberships a User holds is derived by querying, not stored redundantly, same reasoning as Section 2.9's "roles are derived, not stored on Party."
- **`Role`** — `OWNER_ADMIN`, `ACCOUNTANT`, `APPROVER`, `READ_ONLY`, `COMPLIANCE_ETHICS_REVIEW`, quoted directly from the spec's Section 7.8 RBAC baseline ("RBAC at minimum: Owner/Admin, Accountant, Approver, Read-only, plus a Compliance/Ethics-review role"), not invented. A label enum only — no permissions matrix exists anywhere in the spec, and permission *enforcement* is explicitly an API-layer concern (spec 7.8/8.2), not built here. `COMPLIANCE_ETHICS_REVIEW` is described in the spec as Purse-specific in origin ("for Purse's board-review and grey-area escalation workflow") but kept in this shared enum rather than split out the way Lending was (Section 2.3) — unlike Lending, it carries no Purse-specific *behavior* here, just an unused label for non-Purse tenants, so it doesn't compromise the GL Engine's genericness.
- **`Membership`** — `id`, `userId`, `tenantId`, `role`, plus a self-tracked `status: MembershipStatus` (`ACTIVE`/`REVOKED`, not spec'd anywhere — a minimal default matching `Account`'s own `active`/`deactivate()`/`reactivate()` precedent, **bidirectional** unlike `GoingConcernStatus`'s deliberately one-way transition, since no confirmed policy blocks re-granting access to someone who left and came back). `Membership.grant(userId, tenantId, role)` is the factory — this is the concrete aggregate `Tenant`'s `_adminMembershipIds` set has referenced by ID since `Tenant` was built (Section 9.6 flagged it as not yet built; now it is). **Tenant-scoped only, not Company-scoped within a Tenant** — the spec's own data model defines Membership as "Join of User + Tenant + Role," with no per-Company access variation described anywhere, confirmed via the same spec check.
- **Deliberately deferred, confirmed out of scope:** the invitation/onboarding flow (spec 7.8 names it in one bullet with zero further detail — no states, tokens, or email mechanics anywhere in the spec), `OnboardTenantUseCase`/`AddCompanyToTenantUseCase` (application-service layer, nothing built there for any aggregate yet), and any actual permission-check enforcement (explicitly an API-layer concern per spec).

### 3.3 Lending context (Purse-specific)

**LoanProduct** — product type, APR ceiling, rate-breakdown components. Not yet built.

**ArrearsCase — core built and tested 2026-08-12.** `com.theprodeogroup.fish.domain.lending.ArrearsCase`, 13 passing tests, 155 total in the repo. Built directly from `docs/UK/Purse Credit Union - Ethical & Theological Framework.docx`'s "Arrears Management Process" — the stage names, day-overdue thresholds, and per-stage remedy options are quoted from that document, not invented: **Early Contact** (1-7 days overdue), **Pastoral Engagement** (8-30 days — payment plan restructure, payment holiday max 3 months, interest-only short-term, financial counseling referral), **Formal Review** (31-60 days — consolidation/refinancing, extended term, partial forgiveness, voluntary asset liquidation), **Final Resolution** (60+ days — board decision matrix, "can't pay" vs. "won't pay," legal action requires board approval).

- **`ArrearsStage`** — strictly linear `canTransitionTo()`, matching `PostingStatus`/`PeriodStatus`'s convention; day-count thresholds themselves aren't enforced inside the aggregate (a wall-clock/application-layer concern, same boundary `JournalEntry` already draws against `Period`).
- **`ArrearsOutcome`** — `RESTRUCTURED`, `PAYMENT_HOLIDAY_GRANTED`, `PARTIAL_WRITE_OFF`, `FORMAL_COLLECTION`. Deliberately generic, not one value per exact source-document menu item.
- **Confirmed 2026-08-12, resolving a real gap in the source material itself** (the ethical framework doc never states whether an early-stage remedy closes a case): **a case can resolve at *any* stage** via `resolve(outcome)`, not only at Final Resolution — `isResolved` is driven by whether `outcome` is set, independent of `stage`.
- **`escalate(company: Company?)` calls `Company.flagSubstantialDoubt()`** when a business borrower's case (`companyId` set) reaches `Final Resolution` — the concrete implementation of the linkage `Company`'s own KDoc has referenced since Section 9.7 (built 2026-08-11, "awaits Lending"). Requires the actual `Company` object, not just its ID, matching `PurchaseOrder.send(creditor)`'s established pattern; fails with `ValidationResult.failure` if a business borrower reaches Final Resolution without the matching `Company` being provided. A `Company` already in `SUBSTANTIAL_DOUBT` (e.g. from a different case) failing to re-flag doesn't block *this* case's own escalation — not a real failure of the operation.
- **`companyId: CompanyId?`** is set only for business borrowers; `borrowerId: BorrowerId` is a reference-only ID with no `Borrower` aggregate behind it yet, same precedent as Payroll's `EmployeeId` (Section 2.7) and consistent with the Party-Role design (Section 2.9) not being built.
- **Domain events**: `ArrearsStageChanged` (on every escalation) and a newly-added `ArrearsCaseResolved` (on resolution, at any stage) — not previously named in Section 4, added here since resolution is a distinct consumer-relevant moment from a stage escalation.

**Deliberately deferred, confirmed out of scope for this increment:** `CAPITALIZED_TO_EQUITY` as an outcome and the `EquityStake` hand-off (`DebtCapitalized` event) — business-only, and neither the mechanism nor `EquityStake` itself exist in enough source detail to build correctly (the capitalization concept is Spec-only, Section 7.13, absent from all three UK source documents). Also deferred: the **"Jubilee" 7-year write-off model** for individual members (Spec Section 7.9) — barely documented ("every 7 years, Board reviews long-standing unpaid debts") and a genuinely different mechanism from business capitalization, not a variant of it. `LoanProduct` itself also remains unbuilt — `ArrearsCase` references a loan via a plain `loanAccountId: AccountId`, not a `LoanProduct`.

**Deployment topology — resolved 2026-08-12, see Section 2.3.** Lending/Credit Union Software is confirmed to belong in its own separate repository, not a package of the GL Engine — `ArrearsCase` currently sits in this repo's `domain.lending` only because it was built before that was confirmed. Extraction itself is deliberately deferred as its own piece of work (see Section 2.3) — don't build anything further here assuming it stays.

**EquityStake** — conversion date, converted amount, resulting ownership percentage, valuation basis, status (`Under Administration` / `Turnaround In Progress` / `Exited`). Not yet built (see above). Expected to transfer to/be co-managed with Scrip once created (spec Section 7.13/11.1) — FiSH's job is to record the conversion accurately, not to manage the turnaround.

## 6. First TDD Test Specifications (not yet executable — see tooling note)

Written given/when/then, ready to become Kotest `DescribeSpec`/`BehaviorSpec` or plain JUnit5 tests once a build exists. Recommended build order: **Money → Account → Period → JournalEntry** (each depends on the previous).

### Money
- Given two `Money` values in the same currency, when added, then the result has the summed amount and the same currency.
- Given two `Money` values in different currencies, when added, then it fails (exception or `ValidationResult.failure`, matching existing convention) rather than silently producing a wrong number.
- Given a `Money` value, when compared to another in a different currency, then comparison fails rather than silently comparing raw amounts.

### Account
- Given a valid Company ID, account type, code, and name, when an `Account` is created, then it's active and has no parent.
- Given an existing `Account` with posted `JournalEntry` history, when deletion is attempted, then it's rejected — deactivation is offered instead.
- Given a child `Account`, when its parent is looked up, then the hierarchy resolves correctly (no cycles allowed — a creation-time check).

### Period
- Given a new `Period` in `Draft`, when opened, then status becomes `Open` and `allowsPosting()` is true.
- Given an `Open` `Period`, when closed, then status becomes `Closed` and `allowsPosting()` is false.
- Given a `Closed` `Period`, when reopened, then status returns to `Open` (per `canReopen()`).
- Given a `Locked` `Period`, when any transition is attempted, then it fails — `Locked` is terminal, per the existing `PeriodStatus` rules.

### JournalEntry
- Given a set of lines where total debits equal total credits (same currency), when the entry is validated, then validation succeeds.
- Given a set of lines where debits ≠ credits, when validated, then validation fails with a clear error (via `ValidationResult`, not a silent post).
- Given a `Draft` entry, when posted, then status becomes `Posted`, a `JournalEntryPosted` event is recorded, and further edits are rejected (`isEditable()` becomes false).
- Given a `Posted` entry, when posted again, then it's rejected (`canTransitionTo` only allows `Posted → Reversed`).
- Given a `Draft` entry whose target `Period` is `Closed`, when posting is attempted, then it's rejected by the `PostingService` (not by `JournalEntry` itself, per the Section 3.1 design note).
- Given a `Posted` entry, when reversed, then a new `Reversed`-sourced entry is created referencing the original, and the original's own status becomes `Reversed` — the original is never deleted or edited in place.

## 9. Tenant Onboarding Flow

Two genuinely different onboarding paths share the same underlying aggregates but differ in who triggers them and how much friction is appropriate:

- **Internal venture provisioning** — Purse (one Tenant, four Companies: UK, NI, ROI, SL — Section 8), Scrip, Osusu, and BuzzMe once scoped. White-glove, done by FiSH/Purse ops, not self-serve.
- **External B2B SaaS signup** — the Mano River SMB wedge (spec §2.6). Closer to self-serve, KYB-gated, typically a single Company at first.

Both paths run the same core use case with different defaults/friction, not two different domain models.

### 9.1 Two distinct use cases, not one

"Onboarding a tenant" and "onboarding a company" are different weights of operation and should stay separate application services:

- **`OnboardTenantUseCase`** (rare — once per venture or per external customer): creates the `Tenant`, its first `Company`, the first admin `User` + `Membership`, and records the initial KYB outcome. Heavyweight, happens a handful of times.
- **`AddCompanyToTenantUseCase`** (more frequent): adds another legal entity to an *existing* Tenant — e.g., Purse adding its Sierra Leone entity after UK is already onboarded. Lighter: no new admin Membership required, inherits the Tenant's settings, only jurisdiction-specific fields (currency, fiscal calendar, COA template variant) are new inputs.

Collapsing these into one flow would force every "add a jurisdiction" operation to re-walk full Tenant-level KYB and admin-invitation steps it doesn't need.

### 9.2 `OnboardTenantUseCase` — step by step

1. **Capture Tenant identity**: legal/group name, tenant segment (internal venture vs. external B2B customer — drives which defaults and friction level apply), primary jurisdiction, base currency, fiscal calendar.
2. **Create `Tenant`** in an initial not-yet-active status (see 9.3) — mirrors the existing convention of encoding lifecycle state in the type itself (`PostingStatus`, `PeriodStatus`).
3. **Create the first `Company`** under that Tenant: legal entity name, `ClientType` (Purse's UK/NI/ROI/SL Companies use `NON_PROFIT` — resolved 2026-08-11, see Section 8), jurisdiction. `ClientType` selects the default COA template (spec §7 mentions per-`ClientType` COA templates already) — note the flag in Section 8 about the `NON_PROFIT` template's fit for a credit union's actual account structure.
4. **Create the first admin `User` + `Membership`** (User × Tenant × Role=Owner/Admin) — the person who can subsequently use the spec §7.8 invitation flow to add more users, so onboarding only ever needs to create one user, not enumerate the whole team.
5. **Record KYB/AML outcome as metadata, and KYC on the admin from step 4** — per spec §5.2 (out of scope) and §7.11, FiSH does not perform screening, only records the outcome and gates on it. **Resolved (2026-08-11): this step is two checks, not one** — `kybStatus` (the business-level KYB check) and `adminKycStatus` (personal KYC on the admin `User` created in step 4), each independently `Verified`/`Pending`/`Flagged`. **Why (user, 2026-08-11): AML.** Anti-money-laundering regulation is what actually requires identifying and verifying the individual(s) who control a business, not just the business entity itself — "verify the business" without "verify who runs it" leaves the exact gap AML rules exist to close (a shell business with an unverified controller). So the founding admin's KYC isn't optional polish on top of KYB, it's a component AML compliance requires — captured here, as part of onboarding, not deferred. This is *not* the same as the *Client*-level common-bond/KYC declaration in §7.11, which only applies to members onboarded later (a different population, once the Tenant is already Active) — the admin created at onboarding is a special case precisely because AML cares who controls the Tenant from day one.
6. **Issue a Tenant-scoped API key** if the Tenant will integrate programmatically (Scrip, Osusu, a future USSD gateway) — optional at onboarding time, can be deferred.
7. **Activate**: once minimum requirements are met (≥1 Company, ≥1 admin Membership, recorded `kybStatus`/`adminKycStatus`), transition `Tenant` to `Active`. **Resolved (2026-08-11): neither KYB nor admin KYC verification blocks activation** — a Tenant with `Pending` `kybStatus` and/or `adminKycStatus` (or even not-yet-`Verified`) can go `Active` immediately. Both instead run on a shared **180-day grace-period clock** — see 9.4. (`Flagged` on either one still gates activation.)
8. **Emit `TenantOnboarded`** (new domain event, add to the Section 4 list) for downstream consumers — billing, reporting, audit trail.

Steps 2–5 happen inside one application-service transaction boundary even though `Tenant`, `Company`, `User`, and `Membership` remain separate aggregates persisted separately (per Section 3.2 — `Company` is referenced by ID from `Tenant`, never embedded).

### 9.3 `TenantStatus` — new state machine

Doesn't exist in code yet; needs the same "encode transitions inside the type" treatment as `PostingStatus`/`PeriodStatus`. **Revised 2026-08-11**: no `PendingVerification` state — since neither KYB nor admin KYC gates activation (9.2 step 7), a lifecycle stage named after verification would be misleading dead weight. Verification progress is tracked as its own fields/clock on the Tenant (9.4), orthogonal to `TenantStatus`:

- `Draft` → `Active`
- `Active` ⇄ `Suspended` (reversible — e.g., non-payment, a KYB or admin-KYC flag raised post-activation, **or the 180-day grace period lapsing unverified — see 9.4**)
- `Active` / `Suspended` → `Closed` (terminal — customer offboarding; data retained per spec §7.15 retention policy, never deleted on close)

Every transition should produce an `AuditAction` entry, consistent with how the rest of the domain treats state changes.

### 9.4 Verification grace period (new, 2026-08-11; revised same day to cover admin KYC)

Resolved: a Tenant activates immediately regardless of `kybStatus`/`adminKycStatus`, but both are expected to reach `Verified` within a **180-day grace period** from activation, tracked separately from `TenantStatus`:

- **Fields on `Tenant`**: `kybStatus` (business-level check) and `adminKycStatus` (the founding admin's personal check, step 5) — each `Pending`/`Verified`/`Flagged` — sharing one `kybVerificationDeadline` (activation date + 180 days). **Resolved (2026-08-11): tracked as two independent fields, not one combined status** — they can clear at different times or via different verification providers. Both use the same activation rule (`Pending` doesn't block, `Flagged` does) and the same deadline; the grace period is only cleared once *both* reach `Verified`.
- **Reminders**: scheduled prompts to the Tenant's admin `User`(s), escalating as the deadline approaches. **Resolved (2026-08-11): day 90 (halfway), day 150 (30 left), day 166 (14 left), day 173 (7 left), day 179 (1 left)** — five touchpoints total, counted from activation. Uniform across all tenant segments (internal venture and external B2B alike) — not configurable per segment; this was a deliberate simplicity choice, not an oversight.
- **Deadline enforcement**: a scheduled application-service sweep (not aggregate-internal logic — same "domain service checks and validates" pattern already used for `Period`/`PostingService` in Section 3.1) checks for Tenants past `kybVerificationDeadline` where `kybStatus` and/or `adminKycStatus` is still not `Verified`, and transitions them `Active → Suspended`, with an `AuditAction` recording the automated reason (distinct from a manually-triggered suspension).
- **New domain event** (add to Section 4's list): `KYBGracePeriodExpired`, fired on that automated suspension, so billing/notifications can react. One event covers either field lapsing — not split into separate KYB/KYC expiry events, since the outcome (suspension) is identical either way.

### 9.5 Still open before this can become code

Every decision point raised across Sections 9.1–9.4 is now resolved (Tenant/Company boundaries and `ClientType` — Section 8; KYB-vs-activation and the grace-period cadence — 9.4). Nothing left blocking this flow from becoming real code. One residual, non-blocking item:

- Purse's `ClientType` is resolved (`NON_PROFIT`, Section 8), but its default COA *template* content still needs credit-union-specific work before step 3 produces a chart of accounts that actually fits a credit union's books, not a charity's. Template-content work, not a design gap.

### 9.6 Implementation status (2026-08-11)

The `Tenant` aggregate itself is **built and tested** — `src/main/kotlin/com/theprodeogroup/fish/domain/tenancy/` (`tenant.kt`, `tenant_status.kt`, `tenant_segment.kt`, `verification_status.kt`, `tenant_events.kt`, `ids.kt`), 29 passing tests across `TenantTest.kt` and `TenantStatusTest.kt`. Covers: `onboard()` (bare Draft, no Company/Membership yet — Section 9.2 steps 1–2), `addCompany()`/`addAdminMembership()`/`recordKybOutcome()`/`recordAdminKycOutcome()` (steps 3–5), `activate()` (step 7 — rejects on missing Company, missing admin Membership, or Flagged `kybStatus`/`adminKycStatus`, combining all four via `ValidationResult.combine()`; succeeds when both are still Pending; starts the shared 180-day deadline; raises both `TenantActivated` and `TenantOnboarded`, since this one call is steps 7+8), `suspend()`/`reactivate()`/`close()`, and `isKybGracePeriodExpired()`/`suspendForExpiredKyb()` for the 9.4 scheduled sweep (expired if *either* field is still unverified past the deadline). `KybStatus` was renamed to `VerificationStatus` when the admin-KYC field was added, since the type is now shared by both checks.

### 9.7 Going-concern status on Company (new, 2026-08-11)

Clarification from the user during this session: "going concern" is the accounting term itself — the assumption that a business will continue operating, not a synonym for "has pre-existing history." It applies equally to a brand-new Company being onboarded (intended to operate ongoing) and an established one bringing in prior books. So this isn't a special onboarding path or a fork in `OnboardTenantUseCase` — it's a status every `Company` carries from the moment it's created, defaulting to the standard assumption.

- **`GoingConcernStatus`** (new enum, `domain.tenancy`, not yet built in code): `ASSUMED` (default — no known events raising doubt) and `SUBSTANTIAL_DOUBT` (mirrors real audit language: "substantial doubt about the entity's ability to continue as a going concern").
- **Lives on `Company`, not `Tenant`** — resolved 2026-08-11. Going concern is a legal-entity/books-level accounting assessment (financial statements are prepared per Company), and a single Tenant can hold Companies with different statuses (e.g., one of Purse's four Companies could be in distress while the others aren't) — a Tenant-level field couldn't represent that. **Concrete case from the user, same day:** a Tenant running a conglomerate/group structure may deliberately designate one Company as a loss-leader — its losses are a strategic choice, not doubt about the group's ability to continue. A Tenant-level status would either wrongly flag the whole group over one intentionally-unprofitable subsidiary, or hide a real per-Company signal entirely. Per-Company tracking is what makes "this one subsidiary is fine being unprofitable" representable at all.
- **Default assignment**: Section 9.2 step 3 (create the first `Company`) sets `goingConcernStatus = ASSUMED`. No activation gate depends on it — a Company starts `ASSUMED` and stays that way unless something specific changes it.
- **What changes it**: resolved 2026-08-11 — **tied to the Lending context's `ArrearsCase`, not a standalone mechanism.** When a business borrower's `ArrearsCase` (Section 3.3) reaches `Final Resolution` — the most severe stage, where outcomes like partial write-off, formal collection, or capitalization into an `EquityStake` happen — the borrowing `Company`'s `goingConcernStatus` moves to `SUBSTANTIAL_DOUBT`. The earlier stages (Early Contact, Pastoral Engagement, Formal Review) don't trigger this; they're not yet indicative of real going-concern risk, and firing this on every arrears case would make the flag meaningless noise.
- **Open, not decided**: whether/how a Company moves back from `SUBSTANTIAL_DOUBT` to `ASSUMED` (e.g., if the `ArrearsCase` resolves via restructure, or the resulting `EquityStake` reaches `Exited` per a successful turnaround). Auto-reverting the same way it auto-triggers is one option; requiring an explicit accountant/compliance re-assessment before clearing it is another, and probably the safer default given this is meant to reflect real financial-statement risk, not just cause-and-effect bookkeeping — worth a decision before this gets built, not assumed.
- **Not built yet** — this is design only. `Company`, `ArrearsCase`, and `EquityStake` don't exist in code (Section 9.6 confirms only `Tenant` is built so far).

### 9.8 Onboarding an established Company: the anchor date (new, 2026-08-11, partially resolved)

Separate from going-concern status (9.7) — this is about a Company that has pre-existing books, which needs its history brought into FiSH somehow before normal posting makes sense. A brand-new Company just activates at zero balances (already covered by 9.2); this section is the established-Company case flagged as a gap when onboarding was first discussed.

**Resolved:**
- **Anchor date** (the user's term — use this, not "cutover date") — an administrator-chosen date. Cash and Bank account balances *as at* the anchor date become the opening balance for those accounts in FiSH — i.e., an opening-balance `JournalEntry` (needs its own `JournalSource` value, not yet added — `IMPORT` is close but generic; consider a dedicated value) dated at the anchor date, posted before any normal activity.
- **Accounts Receivable / Accounts Payable are itemized, not a lump sum** — resolved 2026-08-11. Each open invoice (AR) or bill (AP) as at the anchor date is captured individually: counterparty, amount, due date, reference — not just a single AR/AP total. This is unlike Cash/Bank, which is one balance figure.

**Resolved 2026-08-11 — routed to a new module, not decided as core-Ledger scope:** AR/AP accuracy (both ongoing and opening/historical figures) is owned by the planned **Purchase Order Processing / Sales Order Processing** modules (Section 2.5), not by a bespoke onboarding import mechanism and not by a subledger built directly into core Ledger. The same modules used for ongoing operations are also how opening AR/AP figures get entered — one mechanism for both, not two. This is *why* progressive/incremental entry (below) makes sense: it's normal usage of an operational module, not a special onboarding-only allowance.

AR/AP items "can be entered on an ongoing basis till the final accounts are prepared and the year is closed" — explicitly framed by the user as a UX/accessibility choice ("allowing for this makes the software easy to use for non-accountants"), and a general product principle worth applying beyond this one feature (see the "why" note in memory).

**Plain-language framing (2026-08-11):** for a non-accountant entrepreneur specifically, the opening-balance entry for AR/AP shouldn't be presented using accounting jargon at all — the user's own framing: ask for "the list of people who owe him" (AR) and "the people he owes money [to]" (AP), entered day-to-day through the first year, before EOY balances are closed. `AccountsReceivable`/`AccountsPayable` (or whatever the domain model ends up calling these once Purchase/Sales Order Processing is designed) should stay proper accounting terms internally — needed for correctness, reporting, tax, audit — but the entrepreneur-facing UI copy/labels are a separate presentation-layer concern and should use this kind of plain language, not the jargon. Worth carrying forward whenever the PO/SO modules' UI gets designed, not just as a one-off phrasing note.

**Still open:** Section 2.5's own scope — Purchase/Sales Order Processing aren't designed yet beyond the confirmed Customer/AR and Creditor/AP mapping (Section 2.5), including how these modules post into Ledger (Account/JournalEntry). Onboarding's role narrows to: point the admin at these modules for opening AR/AP figures once they exist, and (per 9.8's earlier resolution) handle Cash/Bank directly via a single opening-balance `JournalEntry` at the anchor date, since Cash/Bank doesn't need order/item-level tracking the way AR/AP does.

## 10. Persistence & Multi-Tenancy Strategy (new, 2026-08-11)

Nothing in `infrastructure` exists in code yet (Section 5 — repository interfaces belong in `domain`, implementations were deliberately deferred). This section records the decision so it's not re-litigated when that work starts.

**Resolved: PostgreSQL**, chosen for the reason double-entry bookkeeping actually needs it — a `JournalEntry`'s lines must commit together or not at all, which wants a database with strong ACID transactions, plus the domain is already relational by nature (typed IDs, `Tenant` → `Company` → `Account` → `JournalEntry` references).

**Correction to the reasoning below (2026-08-11, same day):** an earlier pass of this section treated RLS as addressing the noisy-neighbor concern. That was wrong and got corrected in conversation — **RLS is a row-filtering access-control mechanism only.** It stops Tenant A's queries from seeing Tenant B's rows; it does nothing about physical resource contention. Tenants on RLS-protected shared tables still share the same table files, indexes, `shared_buffers` cache, disk I/O, WAL, connection pool, and autovacuum/background-writer processes — a write-heavy tenant bloating a shared table still degrades everyone else sharing it, RLS or not. Also worth recording: schema-per-tenant or database-per-tenant *on the same Postgres instance* only partially solves this either — separate tables/indexes reduce bloat cross-contamination, but `shared_buffers`, WAL, and `max_connections` are cluster-wide in Postgres, not per-database. Full elimination of noisy-neighbor effects needs separate compute (a genuinely separate server instance per tenant), a much bigger step than "recreate a schema."

**Resolved: PostgreSQL native table partitioning by `tenant_id`**, not schema-per-tenant, not database-per-tenant, and not relying on RLS for the resource-isolation problem (RLS still applies on top, for the access-control property it's actually good at). Reasoning:
- Partitioning gives each tenant (or tenant group) separate physical storage and indexes *within one logical table, one database, one migration surface* — no per-tenant schema-recreation ceremony, which the user explicitly wanted to avoid unless performance or regulatory reasons forced it.
- This meaningfully reduces the bloat/cache-eviction side of the noisy-neighbor problem (the part schema/DB-per-tenant would have partially addressed anyway) without paying the migration-multiplication or connection-pool-multiplication costs those patterns carry.
- **Does not** solve CPU scheduling, `shared_buffers` cache, or `max_connections` contention at the instance level — that residual risk is accepted for now, consistent with FiSH's expected shape (a long tail of small SMB tenants, not many large write-heavy ones). Revisit if it becomes a real problem rather than over-building for a risk that may not materialize.
- **Elegant side effect, worth acting on:** partitioning strategy can double as the answer to the Purse regulatory question below — a hybrid scheme (a dedicated `LIST` partition for named large/regulated tenants like Purse, `HASH`-bucketed partitions for the general SMB tail) gets physical separation for the tenant that might need it *and* keeps everyone else on the low-ceremony path, in one mechanism rather than two separate ones. Exact bucket count/partition key details are an implementation decision for when `infrastructure` actually gets built, not decided here.

**Still flagged, not decided, but narrower than first framed — a regulatory question, not an engineering one:** the spec commits to "full data isolation between tenants" (§7.7), and Purse is FCA/PRA-regulated. Confirmed 2026-08-11 (Section 2.3): the member-level detail a regulator would actually scrutinize — loan terms, common-bond declarations, KYC — lives in the Lending context ("the banking module"), not in core Ledger's `Account`/`JournalEntry`/`Period` tables, which only hold the financial *effect* (income/expenditure/capital/assets/liabilities). That means this section's partitioning decision may not need to carry the regulatory weight originally assumed — the sharper open question is **the Lending context's own persistence/isolation strategy**, not core Ledger's. Still needs an actual answer from whoever owns Purse's regulatory compliance, but the question has moved: ask about Lending's data, not just Ledger's, before assuming either way.

### 10.1 Infrastructure skeleton (built 2026-08-19)

The first infrastructure code in the repo — confirmed scope before building (three options offered: infra skeleton only, repositories for the core three Ledger aggregates, or a paper design pass with no code; the skeleton was chosen). `com.theprodeogroup.fish.infrastructure.persistence` — **no repository implementations yet**, just the pieces everything else builds on:

- **`DatabaseConfig`** — a HikariCP `DataSource` + Exposed `Database.connect()`, configured entirely from environment variables (`FISH_DB_HOST`/`FISH_DB_PORT`/`FISH_DB_NAME`/`FISH_DB_USER`/`FISH_DB_PASSWORD`/`FISH_DB_POOL_SIZE`). Host/port/database name default to the local dev setup (`fish_dev` on `localhost:5432`) since none of those are secrets; user/password have **no default at all** and throw (`error()`) if missing — there's no safe default for a credential. No credential of any kind is committed to source control.
- **`DatabaseMigrator`** — a thin wrapper over Flyway, migrations at `src/main/resources/db/migration` (standard `V1__description.sql` naming). `V1__baseline.sql` is deliberately trivial (one marker table) — it exists only to prove the Gradle → Flyway → Postgres pipeline works end to end, not to define real schema. Real tables land incrementally as repository implementations get built, not as one big upfront migration.
- **A separate `integrationTest` Gradle source set/task**, not run by `gradle test` — the existing 336 domain tests stay hermetic (no external dependencies, safe on any machine/CI without Postgres running). `gradle integrationTest` is opt-in and needs `FISH_DB_USER`/`FISH_DB_PASSWORD` set; the one test in it (`DatabaseMigratorIntegrationTest`) skips (via JUnit `Assumptions`, not a failure) if those aren't set, so a fresh checkout with no local database configured doesn't hard-fail.
- **`.env.example`** documents the required environment variables (no real values); `.env`/`.env.local` are gitignored.
- **Verified against a real local Postgres 18 instance**, not just compiled — `gradle integrationTest` was actually run against a `fish_dev` role/database created for this purpose, confirmed via `psql` afterward: `flyway_schema_history` shows migration `1` (`baseline`) succeeded, and `schema_baseline` holds its marker row.
- **New Gradle dependencies:** Exposed 0.56.0 (`exposed-core`/`exposed-dao`/`exposed-jdbc`/`exposed-java-time`), PostgreSQL JDBC driver 42.7.4, HikariCP 5.1.0, Flyway 10.20.1 (`flyway-core` + `flyway-database-postgresql`, split apart from `flyway-core` since Flyway 9).
- **Deliberately not built:** any repository interface or implementation, any real domain-table schema, the `tenant_id` partitioning scheme itself (the decision above is recorded, not yet expressed as actual DDL). Confirmed as the next real steps when this resumes.
