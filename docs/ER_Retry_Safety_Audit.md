# Education Runtime retry-safety and concurrency audit (task F5)

**Status:** 2026-10-13, **findings only; no code.** Written by the Education Runtime (+ER) session for Playbook task F5 ("foundations first": idempotency and concurrency before the features that lean on them). Method: a read-only sweep of every state-changing route (POST, PUT, DELETE; there are no PATCH routes) in `fish-education-runtime` (`Application.kt` and the assessment and first-admin route files), the services and Exposed stores behind them, and the Flyway unique indexes V1 to V36, done by a delegated read-only agent. **Evidence tags:** **[verified]** I re-read the cited code myself; **[reported]** the agent's finding, not independently re-checked yet. Nothing was run against a database.

## 1. Headline

- Of about 50 write routes, **most are safe on a retry** because of a natural-key unique index, an upsert, a deterministic id or a state-machine guard. **Only two paths use a real claim-token idempotency ledger**: `POST /sync/push` (attendance) and the mark routes (`mark:<opId>`). **No route accepts an `Idempotency-Key` header.**
- A **safe-but-errors** retry (a second identical request is refused with a 409 or 400 and nothing is duplicated) is common, and it **hides the id the first call created**: WEB must recover from the matching list read. Returning the existing resource when the request is identical would be kinder (decision A below).
- **Real defects** (a retry or a concurrent call duplicates or loses data): rooms with no id, class transfer not atomic, admissions transitions without compare-and-swap, timetable create under concurrency, student create and CSV import under concurrency, legacy `publish` overwriting a grade, and the guardian-to-SOP customer call (already covered by the design note's key).

## 3. What is already sound (so nobody re-checks it)

Provisioning (`POST /schools`, first admin), staff assignment and revocation (an advisory lock plus a unique index), device registration (a partial unique index backstops the check), teachers, teacher-subject assignments, terms, fee schedule and invoices (unique keys; a loser gets 409, never a duplicate), curriculum topics, progress and scheduled lessons, attendance marks (unique index plus a per-school lock), the S1 set-up routes (scales, structures, offerings), **mark entry, batch and submit (explicit lock order, a claim ledger, an optimistic version)**, and `POST /sync/push` (the claim-first ledger).

## 4. Decisions and the order

- **A. A byte-identical retry of a create returns the existing resource (200), not a 409 or 400** (devices, invoices, admissions, timetable without an id). Proposal: yes, so WEB and the offline app never lose an id. Needs CM's nod because it changes a response code; additive for clients that already handle both.
- **B. Add an optional `Idempotency-Key` header to the create routes** (so far only the sync paths have a ledger), reusing the existing claim-first ledger. Proposal: add it for rooms, timetable lessons, admissions, invoices and guardian resolve, after R2 to R7.
- **Order:** R2 and R3 first (data loss and wrong answers, small), then R4, R5, R7, then R6, then R8 to R10; R1 is task F1; R11 is dropped when payments move to SOP; R12 and R13 are cleanups. **None of these needs a Femi decision** and all are fixes of defects, so they can be built as soon as CM clears the review level (R2, R3, R6 and R9 touch concurrency and idempotency, HIGH).
- **For the offline app (F11, F12):** the sync paths are the safe ones; the create routes the app will call (admission capture in P2, timetable, rooms) need R3, R4, R5 and decision A first.
- **Tests per fix:** a real-Postgres concurrency test (two threads) and a retry test (the same request twice, and after a simulated lost reply), per the standing rule for concurrency paths.

## 5. What this audit did not do

It did not run anything. The findings tagged *reported* need a second read before a fix is cut. It did not audit WEB's retry behaviour, the SOP, EA or HR clients, or the outbox relay (not built).
