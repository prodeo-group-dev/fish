# The shared minimum audit record (RBAC SPUTO R10 and T17), EA's design

**Status:** 2026-10-15, design only, nothing built. Written by the EA session, which owns this shape (RBAC SPUTO T17); each service adopts it in its own task T22. CM asked for it docs-first so that downloads of documents, fixed assets and payroll approvals share one record. **Decisions are asked of Femi in section 7.** Facts about existing code were read on master on 2026-10-15: POP's live `pop_audit_log` (migrations V14 and V15), GL's `AuditLogEntry` (domain class), the RBAC SPUTO (R2, R3, R9, R10, T22) and the Education Runtime playbook's PL-AUD-1. I did not read production data.

## 1. What the record is for

"Who did what, to which thing, at which Company, when, and with whose authority." It must answer three questions without reading code: (1) who approved this payment or payroll run, and was it the same person who raised it; (2) who changed this person's access or this threshold, from what to what; (3) who downloaded this document, and when. It is a **minimum** every service writes; a service may add its own columns, never fewer.

## 2. The record (one row per audited act)

| Field | Meaning | Rule |
|---|---|---|
| `id` | the row's id (UUID) | generated by the writer |
| `occurredAt` | when the act committed (UTC) | taken from the server clock, never from a request |
| `tenantId`, `companyId` | where | Company is null only for a Tenant-wide act (for example a Tenant-level invite); a Company-scoped act always carries it |
| `actorKind` | `HUMAN`, `SERVICE`, `PORTAL` (a link token such as a supplier link) | closed list |
| `actorUserId` | EA's stable user id (`/me` `userId`) for a HUMAN; the service identity's name for a SERVICE; the link's subject id for a PORTAL | never from a request body |
| `actorEmail` | the canonical email (trim, lower-case, RBAC R9) for a HUMAN; null otherwise | the only place an email appears |
| `actedBy` | for a SERVICE act: the origin system and the origin record, for example `{system: "ER", ref: "invoice-123"}`; null otherwise | a service may enter a record but never approves one (R2) |
| `action` | a verb from the service's closed list, upper snake case (`CREATED`, `APPROVED`, `REJECTED`, `REVOKED`, `MODULES_CHANGED`, `DOWNLOADED`, `POSTED`, ...) | one list per service, published in its playbook |
| `entityType`, `entityId` | what the act was done to | strings, as POP's and GL's records already do; the id is the service's own id |
| `before`, `after` | for an access, threshold or setting change only: the old and the new value, as short JSON (roles, modules, an amount limit) | never a secret, a token, a password or a whole document; null for other acts |
| `selfApproved` | true when the approver is the person who raised it (the Owner, flagged per D6) | false by default |
| `requestKey` | the request's `Idempotency-Key` or `X-Request-Id` | lets a retry and the log line be matched |
| `detail` | a short, non-secret, human sentence | free text, bounded (for example 500 characters), never personal data beyond the actor |

## 3. Rules that make it trustworthy

1. **Written in the same database transaction as the act.** The act and its row commit together or not at all; a missing row after a successful act is a defect (R10).
2. **Append only.** No update and no delete route, no mutator on the domain type; a correction is a new row (as GL's `AuditLogEntry` already does by construction).
3. **The actor comes from the verified token, never from a body field.** For a service act the origin is recorded in `actedBy`.
4. **No secrets and no bulk personal data.** Ids, enum values and bounded text. A document download records which document and who, never its content.
5. **Reads are scoped.** A Company's audit rows are visible to its Owner Admin and to roles granted the view-audit capability at that Company; never across Tenants. (Capability naming belongs to the RBAC plan, T5a; until it exists the Owner Admin only.)
6. **Old rows are not rewritten.** Rows from before a service adopts the shape keep their own columns; the new columns are additive and nullable where history cannot supply them (`actedBy`, `requestKey`, `before`, `after`, `selfApproved`).
7. **Retention.** Kept at least six years, proposed (the Education Runtime playbook's PL-AUD-1 proposes the same); the period is Femi's decision.

## 4. How the existing records map (so adoption is additive, not a rewrite)

| Shared field | POP `pop_audit_log` (live) | GL `AuditLogEntry` (domain class) |
|---|---|---|
| `id`, `occurredAt`, `companyId` | `id`, `occurred_at`, `company_id` | `id`, `occurredAt`, `companyId` |
| `tenantId` | missing (POP is single-Tenant per deployment today); add when multi-Tenant lands | `tenantId` |
| `actorKind`, `actorUserId`, `actorEmail` | `actor_kind`, `actor_user_id`, `actor_email` (already EA's `userId` and email) | `actorEmail` only (no user id: GL has no local user) |
| `action`, `entityType`, `entityId` | `action`, `entity_type`, `entity_id` | `action` (an enum), `entityType`, `entityId` |
| `detail` | `detail` | `detail` |
| `actedBy`, `requestKey`, `before`, `after`, `selfApproved` | missing: additive columns | missing: additive fields |

POP's table already matches the minimum except `tenantId`, `actedBy`, `requestKey`, `before`/`after` and `selfApproved`; GL's lacks the user id and the same extras. Neither needs a data migration, only additive columns and writers.

## 5. EA's own audit (the first adopter)

EA records its own access-control acts with this shape in its own table `ea_audit_log` (EA owns the access model, so its acts matter most): invite, accept, decline, revoke, change of modules, Company registration, Owner Admin phone recorded, verification outcomes, the school-module refusals (as a refused-act row only if Femi wants refusals recorded). Each is written in the same transaction as the change. EA writes it now only after the shape is approved; it needs no other service.

## 7. Decisions asked of Femi

1. Approve this minimum shape (section 2) as the platform's audit record.
2. Retention: six years (proposed), or another period.
3. Who may read the audit trail at a Company: the Owner Admin only for now (recommended), and an auditor role later through the RBAC capabilities.
4. Should a REFUSED act (for example the 422 for granting the Education Runtime at a non-school Company) also be recorded? Recommended: no for ordinary validation refusals, yes for authorisation refusals (a 403), as a separate `REFUSED` action; it costs rows but is what an investigator wants.
