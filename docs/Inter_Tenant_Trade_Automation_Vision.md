# Inter-Tenant Trade Automation — FiSH's Real Definition of "Business Systems Integrator"

**Status**: vision/design-only, 2026-09-13. Nothing built, and — explicitly — nothing should be built toward this yet. This document exists to capture a real, differentiated piece of strategic direction precisely, so it isn't lost, while deliberately keeping it out of the current build queue (Republic of Ireland go-to-market, VAT as the MVP threshold). See the Gating section for the concrete condition that should trigger picking this up.

## The actual definition

"Business Systems Integrator" doesn't mean FiSH becomes an Accenture/Deloitte-style consulting business that stitches together a client's existing third-party software stack (their own CRM, e-commerce platform, external payroll provider). That's a different business model entirely — services-led, headcount-scaled, a different hiring plan and sales motion than a product-led ledger platform.

**The real vision, stated precisely**: when a business that is a FiSH tenant issues a Purchase Order to another business that is *also* a FiSH tenant, that Purchase Order should be able to **automatically become a Sales Order** on the receiving tenant's side — no re-keying, no manual double entry, the transaction propagates because both trading partners already live on the same platform.

**The same capability applies to the Returns cycle, not just the original order (2026-09-16, user direction)**: when Tenant A (the buyer) initiates a Return Outwards against Tenant B in their own POP, that should be able to automatically become a Return Inwards on Tenant B's own SOP - the identical "automatic propagation instead of re-keying" idea, applied to the returns direction rather than the original PO→SO direction. Everything in this document's analysis (the trading-partner consent requirement, the cross-tenant propagation mechanism, the rejection/dispute path, the tenant-isolation boundary below) applies equally to this case - it is not a separate feature, it is the same mechanism used for a second document pair. `ReturnOutwards` lives in POP (`POP/.../V6__returns_outwards.sql`), `ReturnRequest` (Returns Inwards) lives in SOP (`SOP/.../V4__returns_inwards.sql`) - today, entirely intra-tenant, exactly like PurchaseOrder/SalesOrder.

This is a genuine network effect, not a services offering: the value of being a FiSH tenant increases with every other FiSH tenant a business might trade with. It's also a real differentiator from a generic ledger-as-a-service or accounting product — those stop at *your own* books; this connects two businesses' books to each other directly.

## Why this is explicitly gated, not queued

Building the trust/identity/consent machinery this needs (below) has no one to use it until there are real, paying FiSH tenants who actually trade with each other. Building it now would compete directly with the team's current, narrower, immediately-monetizable priority (RoI go-to-market, VAT as the MVP threshold, per `docs/IE/IE_MVP_Definition.md` and `docs/IE/IE_VAT_MVP_Design.md`).

**Concrete gating condition, not a vague "someday"**: revisit this once FiSH has at least two real, paying tenants — Prodeo-affiliated or not — who have actually expressed interest in trading with each other. Before that point, this stays a documented vision, not a roadmap item.

## Why this is a genuinely bigger lift than it sounds

Checked against the real, current architecture, not assumed:

- **POP's `Supplier` and SOP's `Customer` are each scoped to a single tenant's own bounded context today**, with no notion that a Supplier record might correspond to an actual other Tenant/Company elsewhere in FiSH. There is no cross-tenant identity concept anywhere in the current design.
- **Every existing service-to-service call is intra-tenant, and this was deliberately reinforced, not just left alone, on 2026-09-16.** POP→IM, POP→GL, SOP→GL, SOP→IM all authenticate as a service account scoped to one tenant's own resources (the `CognitoServiceAccountTokenProvider` pattern this session fixed a live incident in). That same week, IM and GL's own inbound service-account gates were explicitly built to **permanently bypass EA's Tenant/Membership check** for these callers (`docs/Service_Account_Identity_And_EA_Membership_Design_Note.md` - IM `a022435`/`2daea8a`/`3b4952b`, GL `d376f66`) - on the reasoning that a module-to-module call is *one Tenant's own* GLaaS plumbing, not a business user acting inside a Tenant, so it doesn't need Tenant-level authorization at all. **That reasoning does not extend to inter-tenant calls.** A PO from Tenant A's POP proposing a SO on Tenant B's SOP (or a Return Outwards from A proposing a Return Inwards on B) is not "one Tenant's own plumbing" - it is Tenant A reaching into Tenant B's own boundary, which is exactly the case EA's Membership model - or a new, equivalent trust mechanism - exists to gate. Nothing in the 2026-09-16 service-account work is reusable here as-is; this needs the trading-partner consent layer in the section below, not a copy of `isServiceAccount`.
- **The two line-item shapes don't match today.** `SalesOrderLine` has no item reference at all (`description`/`quantity`/`unitPrice` only — confirmed directly while scoping the VAT design work). `PurchaseOrderLine` has an *optional*, often-absent `itemId`. Auto-creating a SalesOrder from a PurchaseOrder either needs a real catalog-mapping mechanism, or (more realistically for a first version) needs to accept that the auto-created SalesOrder starts as plain description/quantity/price, same as any other SalesOrderLine today — which is actually the *simpler* path, not a blocker, given neither aggregate is deeply Item-coupled yet.
- **Ledgers stay separate, correctly.** Tenant A's Accounts Payable (posted via POP→GL) and Tenant B's Accounts Receivable (posted via SOP→GL) must remain on their own separate books — per-tenant Ledger isolation is a correct, deliberate property of the platform and this feature must not blur it. The automation belongs at the *order/document* layer, not the Ledger.

## What real work this needs (high-level — not a build spec)

Written against the PO→SO case for concreteness, but every item below applies identically to the Returns cycle (Tenant A's own POP `ReturnOutwards` → Tenant B's own SOP `ReturnRequest`/Returns Inwards) - one trading-partner relationship, one propagation mechanism, one dispute path, serving both document pairs, not a second parallel system.

1. **A trading-partner relationship with real consent** — some new concept linking "this Supplier record in Tenant A's POP" to "this actual Tenant/Company in FiSH," established only when *both* sides agree. Without mutual consent, any tenant could spontaneously create sales obligations on another tenant's books — a real abuse vector, not an edge case to wave away.
2. **A cross-tenant propagation mechanism** — how Tenant A's POP actually notifies Tenant B's SOP. Not designed here; candidates worth weighing when this is actually picked up: a mediating service (mirroring how EA already mediates administration across the platform), a direct cross-tenant call once identity+consent exist, or an event/message-bus pattern (likely the better fit for a many-to-many trading network rather than point-to-point calls, but genuinely undecided).
3. **A rejection/dispute path** — the receiving tenant must be able to reject or amend an auto-created SalesOrder, not be forced to honor it. An automatically-created document is a proposal from the platform's point of view until the receiving business accepts it, not a fait accompli.
4. **Item/catalog reconciliation — deliberately deferred, not solved.** Given neither line-item aggregate is deeply Item-coupled today, the pragmatic first version likely doesn't require solving cross-tenant catalog matching at all: an auto-created SalesOrder can carry plain description/quantity/price, same shape as any manually-entered one, with Item-level linkage as a later refinement rather than a prerequisite.
5. **Audit trail and rate limiting** — every auto-created document needs to be traceable to the originating tenant's own PurchaseOrder, and the mechanism needs abuse-resistance from day one, not retrofitted after a problem.

## Open questions — for whenever the gating condition is met

1. **Scope of the trading network**: Prodeo-affiliated businesses only (Purse-adjacent entities that happen to trade with each other), or a genuinely open network between any two unrelated companies that both happen to use FiSH? This is a trust-model decision with real security-surface implications, not a detail — the latter is a much bigger commitment.
2. **How does a trading-partner link get established** — does Tenant A "invite" a specific Tenant B by some identifier, or does FiSH need a directory/discovery mechanism for tenants to find each other? A directory is a materially bigger product surface than simple invitation-by-reference.
3. **Does this become its own bounded context/service**, mirroring the SOP/POP/IM/HR/EA extraction precedent, given its inherently cross-tenant (not single-tenant) nature? Likely yes, but genuinely undecided — flagged for the same deliberate scoping pass those extractions got, not a default.
4. **What happens to the Purchase Order side when the Sales Order is rejected or amended?** Needs a real reconciliation story — the buying tenant's own PurchaseOrder can't just silently diverge from what the selling tenant actually agreed to fulfill.
