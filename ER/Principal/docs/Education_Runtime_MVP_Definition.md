# Education Runtime — MVP Definition

**Date:** 2026-10-01
**Source:** `docs/FiSH-ER-Education-Runtime-Technical-Req-Spec-and-Use-Cases-v0.1.md` (v0.1, 1 Oct 2026) — 230 requirements, 14 use cases, Nigeria-reference with Mano River/Ghana/Gambia country packs. Section 10.1 proposes its own MVP scope (Nigeria pilot, private schools + one school group); this doc cross-tabs that proposed scope against the real, current state of `fish-education-runtime`, confirmed by reading the code directly, not assumed.

## 1. One architectural decision made, not parked

The spec's FIN-INT section (§2.4–2.6, §4.16) describes "the FiSH core" owning billing accounts, invoices, payments, receipt numbering, balances and ledger postings in full, driven by an event contract (`StudentEnrolled`, `BillingRunRequested`, `PaymentReceived`, etc.) and versioned REST APIs. **Decided: "FiSH core" for this purpose is SOP (Sales Order Processing), extended — not a new dedicated GL/AR layer.**

**Why:** GL is deliberately generic (the whole point of the POP/SOP/IM extraction precedent — domain-specific billing logic lives in the extracted service, not the ledger itself). SOP already owns `Customer` and the order-to-cash domain; a fee payer is architecturally a Customer. The Guardian-as-Customer work (BK-FEE-5, 2026-09-23) already made this bet explicitly — "a Guardian is equivalent to a Customer... it is a contract the school has to fulfil" — and built `GuardianAccount.customerId → SOP Customer` on that basis. Building a second, separate AR layer would duplicate SOP's own domain and contradict the extraction precedent everywhere else in this platform.

**What this means concretely:** the real gap isn't "which system is FiSH core" — it's that invoicing and payment-confirmation currently live *inside* Education Runtime's own `FeeService` (`issueInvoice`, `confirmPaymentStub`, its own `FeeInvoice` rows), not in SOP. Reaching the spec's FIN-INT shape means migrating that system-of-record into SOP (real invoice issuance, payment allocation, receipt numbering) and narrowing `FeeService` down to fee rules + clearance policy only, consuming SOP events instead of self-managing invoice state. **This is scoped as real backlog work below (new Epic, FIN-INT), not something to build silently as part of routine Fee Desk work.**

## 3. The one open question this doc does **not** resolve: is full offline-first actually required for MVP?

The spec marks `NFR-OFF-001` (core tasks work offline: attendance, score entry, gate/visitor log, pickup verification, admission capture, cash receipting) as **Must**, and it's a dependency of nearly every other MVP-scoped workflow. Building it for real — encrypted local store on Android/PWA, delta sync with per-record versioning, conflict resolution per entity, resumable uploads, pre-allocated offline receipt-number ranges — is a substantial undertaking on its own, arguably comparable in size to everything else in this MVP cross-tab combined.

This is a genuine product/business call, not an engineering one: it depends on how bad connectivity actually is at the real pilot school(s), and whether a staged rollout (online-only pilot first, offline added once the school/workflow proves out) is commercially acceptable. **Recommendation, not a decision**: scope the MVP's *first* real pilot as online-only with a clear, visible "offline" placeholder (the existing `NoOpOfflineAttendanceSync` pattern, extended consistently across ER-ATT/ER-SAF/ER-FEE's offline-capable tasks), and treat full offline-first as the very next thing built once a specific pilot school's actual connectivity reality is known — rather than guessing at a sync/conflict-resolution design against a hypothetical. This mirrors this project's own "park, don't guess" convention. Needs Femi's call before it's treated as settled.
